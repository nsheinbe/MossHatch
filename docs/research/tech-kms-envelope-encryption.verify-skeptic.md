# Skeptic verification: tech-kms-envelope-encryption

Verifier lens: skeptic (try to refute load-bearing claims from primary sources opened independently).
Date of verification: 2026-09-29. Raw re-fetches: `working-directory/research/kms-vskeptic/` (html/txt/json per source; the analyst's `kms/` folder was not reused as evidence).
Method: curl -sSL with browser User-Agent through the pre-configured proxy (no TLS bypass); Vercel pages fetched with `Accept: text/markdown` (returns the doc source with `last_updated` front matter) and, where a banner was in doubt, as HTML; PDF text extracted with pdfminer.six in a throwaway venv (now deleted); `npm pack` for package source. WebSearch was not usable (session budget of 200 calls was already exhausted), so recent-change hunting used primary changelog / document-history / sitemap pages instead of search.

## Overall

The dossier's load-bearing numbers and quotes all re-derive from primary sources. No claim was refuted. Two nuances change how a few statements should be read (rotation cost in the headline, and the "iad1 = us-east-1" label), one analyst "unverified" item is now resolved (STS session duration), and four recent/important facts were missed (AWS IAM shared-OIDC controls for Vercel's global issuer, Vercel Deployment Policies, direct KMS Encrypt for <=4 KB values, custom audience / Static IPs as extra AWS-side controls).

## Claim-by-claim verdicts (12 load-bearing + extras)

### C1. AWS KMS key = $1/month (also each multi-Region primary and replica); first and second rotation each add $1/month, capped -> CONFIRMED
- https://aws.amazon.com/kms/pricing/ (fetched 2026-09-29): "Each AWS KMS key that you create in AWS KMS costs $1/month (prorated hourly). The $1/month charge is the same for symmetric keys, asymmetric keys, HMAC keys, multi-Region keys (each primary and each replica multi-Region key)..." and "the first and second rotation of the key adds $1/month (prorated hourly) in cost. This price increase is capped at the second rotation, and any subsequent rotations will not be billed."
- https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html says the same ("charges a monthly fee for first and second rotation ... capped at the second rotation").
- Price List bulk JSON (publicationDate 2026-09-11T12:46:01Z): "$1 per customer managed KMS key version" (us-east-1, eu-central-1, us-west-2, eu-west-1, us-east-2 all 1.0 USD).
- The analyst listed the "$1 x up to 3 versions = $3/key-month" reading as unverified; the pricing page wording supports it directly, so it can be treated as confirmed.
- Nuance (correction of framing, not of fact): the TL;DR/summary cost range ($3.00-$3.84 at 1,000 secrets; $3.57-$92.97 at 100,000) is 3 keys with NO rotation surcharge. The recommended design turns automatic rotation ON (365 days), so the key floor is $3 in year 1, about $6 after the first rotation and $9/month from the second rotation (year 3). The dossier's table has the "+$6 steady-state" column, but the headline does not. Immaterial in dollars.

### C2. $0.03 per 10,000 requests (us-east-1), 20,000 free requests/month across all Regions; no monthly charge for generated data keys -> CONFIRMED
- Price List JSON (us-east-1): "$0.03 per 10000 KMS requests in US East (N. Virginia)" = 0.000003 USD/request; "Monthly Global Free Tier for KMS requests" 0-20000 at $0.
- Pricing page: "AWS KMS provides a free tier of 20,000 requests/month calculated across all Regions"; "There is no monthly charge for data keys or data key pairs that AWS KMS generates beyond the charge for the API call."
- Same $0.03/10k and $1/key in eu-central-1, us-west-2, eu-west-1 (and us-east-2) re-checked from their Price List files.
- Not stated by AWS: whether one ReEncrypt is billed as one request. The pricing page and FAQ do not say; "one API call = one request" is the natural reading. The re-wrap cost ($0.30 per 100,000 DEKs) would be $0.60 if it were two. Marked unverifiable-but-immaterial.

### C3. Cost table arithmetic -> CONFIRMED (recomputed)
- Requests/month = 10% writes (GenerateDataKey) + reveals (Decrypt): 1,000 secrets -> 2,100 / 30,100 / 300,100; 100,000 secrets -> 210,000 / 3,010,000 / 30,010,000. After 20,000 free: $0.00 / $0.03 / $0.84 and $0.57 / $8.97 / $89.97. Plus $3 for 3 keys -> $3.00 / $3.03 / $3.84 / $3.57 / $11.97 / $92.97. All match. 30.01M req/month = 11.58 req/s average; 100x burst = about 1.16% of 100,000/s.
- These are the analyst's assumptions (10% writes, 2/30/300 reveals), not sourced facts; the arithmetic is right.

### C4. Default symmetric crypto quota 100,000 req/s shared in us-east-1 (also us-west-2, eu-west-1); 20,000 in eu-central-1 and several others; 10,000 elsewhere; adjustable -> CONFIRMED
- https://docs.aws.amazon.com/kms/latest/developerguide/requests-per-second.html: "Cryptographic operations (symmetric) request rate" applies to Decrypt, Encrypt, GenerateDataKey, GenerateDataKeyWithoutPlaintext, GenerateMac, GenerateRandom, ReEncrypt, VerifyMac; "100,000 (shared) in the following Regions: US East (N. Virginia), us-east-1 / US West (Oregon), us-west-2 / Europe (Ireland), eu-west-1"; 20,000 list = us-east-2, ap-southeast-1, ap-southeast-2, ap-northeast-1, eu-central-1, eu-west-2, eu-south-2; "All AWS KMS request quotas are adjustable, except for the AWS CloudHSM key store request quota". KMS doc history shows the last cryptographic-ops quota increase was 2024-07-08 (no 2026 change).

### C5. Encryption context = AAD, logged in plaintext in CloudTrail, usable as key-policy/IAM condition; the analyst's policy pattern is the documented one -> CONFIRMED
- https://docs.aws.amazon.com/kms/latest/developerguide/encrypt_context.html: "AWS KMS uses the encryption context as additional authenticated data (AAD)... cryptographically bound to the ciphertext"; "The encryption context is not secret and not encrypted. It appears in plaintext in AWS CloudTrail Logs"; kms:EncryptionContext:context-key and kms:EncryptionContextKeys "allow (or deny) a permission only when the request includes particular encryption context keys or key-value pairs".
- https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.html documents exactly "require a pair and forbid all others" = `StringEquals kms:EncryptionContext:AppName` + `ForAllValues:StringEquals kms:EncryptionContextKeys`, and warns ForAllValues alone would allow a request with no context (the paired StringEquals fails in that case). So the dossier's policy shape is right.
- GenerateDataKey doc: same-context requirement, "InvalidCiphertextException" on mismatch, "erase the plaintext data key from memory"; Decrypt doc: "specifying the KMS key is always recommended as a best practice". Confirmed.
- Limit of the control (dossier already says this): the app itself supplies owner_id/secret_id, so a key-policy condition cannot bind a caller to "its own" tenants; it only pins app/env and the shape of the context.

### C6. ReEncrypt runs entirely inside KMS, can change encryption context, needs kms:ReEncryptFrom/To, cannot process Encryption SDK ciphertext -> CONFIRMED
- https://docs.aws.amazon.com/kms/latest/APIReference/API_ReEncrypt.html: reencrypt "under the same KMS key, such as to change the encryption context of a ciphertext"; "it cannot decrypt ciphertext produced by other libraries, such as the AWS Encryption SDK or Amazon S3 client-side encryption"; permissions kms:ReEncryptFrom / kms:ReEncryptTo.
- https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/introduction.html: "The AWS Encryption SDK cannot decrypt the ciphertext that the AWS KMS Encrypt or ReEncrypt operations return", and the reverse.
- The dossier's inference "so skip the ESDK for MVP" is reasonable; strictly the docs show no supported re-wrap path, not a proof that none can exist (an ESDK header is authenticated, so a header edit would need the plaintext data key in your process).
- The analyst left open whether ReEncrypt under the same key ID lands on the current rotated material. rotate-keys.html says "When you use a rotated KMS key to encrypt data, AWS KMS uses the current key material", which implies yes (ReEncrypt = decrypt + encrypt), but the docs do not spell out ReEncrypt; leave as inferred.

### C7. Automatic rotation: default 365 days, range 90-2560, retains all old material until key deletion, no re-encryption, no mitigation of a compromised data key -> CONFIRMED
- rotate-keys.html ("default value is 365 days"; "Key rotation will not mitigate the effect of a compromised data key"; "AWS KMS retains all key material for a KMS key with AWS_KMS origin, even if key rotation is disabled. AWS KMS deletes key material only when you delete the KMS key."); API_EnableKeyRotation.html: "Valid Range: Minimum value of 90. Maximum value of 2560."

### C10. Vercel AWS path (provider URL oidc.vercel.com/TEAM, sub+aud StringEquals, AWS_REGION pin, helper package) -> CONFIRMED, and one unverified item is now RESOLVED
- https://vercel.com/docs/oidc/aws (last_updated 2026-08-28): Team mode provider URL `https://oidc.vercel.com/[TEAM_SLUG]`, audience `https://vercel.com/[TEAM_SLUG]`; trust policy with `oidc.vercel.com/[TEAM_SLUG]:sub` = `owner:...:environment:production` and `:aud`; "AWS_REGION is not stable by default. Vercel sets AWS_REGION automatically to your function's execution region."
- RESOLVED: `npm pack @vercel/oidc-aws-credentials-provider@3.3.9` (npm modified 2026-09-22): the .d.ts documents `durationSeconds=3600` ("Defaults to 3600 seconds") and lets callers override it; the provider is `async () => fromWebToken({...initOptions, webIdentityToken: await getVercelOidcToken(...)})()`, i.e. it is lazy, so constructing the AWS client at module scope (as Vercel's own examples do) is fine; only calling getVercelOidcToken() eagerly at module level is disallowed ("you cannot execute the getVercelOidcToken() function directly at the module level"). The dossier's wording "call the credentials provider inside the request handler" is stricter than necessary. Set `durationSeconds` down to 900-3600 as needed and cap the role max session at 1 h.
- AWS STS doc: "Calling AssumeRoleWithWebIdentity does not require the use of AWS security credentials"; DurationSeconds default 3600, range 900 to role max (1-12 h). Confirmed.

### C11. AWS maps only amr, aud (azp), email, oaud, sub for a generic OIDC IdP; Vercel's project_id/owner_id cannot be conditioned -> CONFIRMED (upgrade from "medium")
- https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_iam-condition-keys.html "Available keys for AWS OIDC federation": "Default lists the standard OIDC claims..."; table rows amr(Yes), aud(azp or aud; Yes), email(No), oaud(No), sub(Yes). Extra per-IdP tabs exist only for Cognito, Login with Amazon, Facebook, GitHub (and Google under Default). Vercel has no tab, so `sub` and `aud` are the only usable Vercel-specific conditions. Because `sub` embeds team slug and project NAME (mutable per Vercel), the dossier's identified weakness stands.

### C12. NIST SP 800-38D: RBG-based IV construction, total invocations per key <= 2^32; revision underway, no draft -> CONFIRMED
- PDF https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf (re-extracted): Sec 8.2.2 "the length of the random field shall be at least 96 bits"; Sec 8.3 "The total number of invocations of the authenticated encryption function shall not exceed 2^32, including all IV lengths and all instances of the authenticated encryption function with the given key" (applies to the RBG-based construction, as the analyst says).
- https://csrc.nist.gov/pubs/sp/800/38/d/final: "Planning Note (03/06/2024): NIST has decided to revise this publication." https://csrc.nist.gov/pubs/sp/800/38/d/r1/2prd: published June 1, 2026; comments closed July 31, 2026; "there is no actual draft document available". New detail: the revision "will remove support for authentication tags whose lengths are less than 96 bits" and proposes a wider wGCM; neither affects the design (16-byte tags, 96-bit random nonce, one use per DEK). Submitted comments were posted 09/01/26.

### C14. iad1 is Vercel's default function region and is labelled us-east-1 -> CONFIRMED as a label; network co-location UNVERIFIABLE
- https://vercel.com/docs/regions (last_updated 2026-08-11): region table columns are "Region Code | Region Name | Reference Location", row `iad1 | us-east-1 | Washington, D.C., USA` (the analyst called it "a label"; it is the "Region Name" column). https://vercel.com/docs/functions/configuring-functions/region: "By default, Vercel Functions execute in Washington, D.C., USA (iad1) for all new projects".
- New detail: the regions page lists a failover order for the default region (iad1 -> cle1 (us-east-2) -> yul1 -> sfo1 -> pdx1 -> dub1 ...), so without a pinned AWS_REGION an outage could send KMS calls to a different AWS Region. The dossier's "pin AWS_REGION=us-east-1" is correct and more important than it looks; note also that a single-Region KMS key is a single point of failure in a us-east-1 event (multi-Region key replica = +$1/month).

### C15. Key deletion 7-30 days (default 30), irreversible; DisableKey immediate (eventual consistency); role-session revoke via aws:TokenIssueTime; policy changes take minutes -> CONFIRMED
- deleting-keys.html ("waiting period of 7 - 30 days. The default waiting period is 30"; "irreversible"); enabling-keys.html ("it becomes unusable right away (subject to eventual consistency)"; data-key-protected resources unaffected until the key is used again); id_roles_use_revoke-sessions.html ("you can immediately revoke all permissions to the role's credentials issued before a certain point in time"; the deny policy uses aws:TokenIssueTime); id_credentials_temp_control-access_disable-perms.html ("It might take a few minutes for policy updates to take effect").
- Runbook-relevant nuance stated by AWS: "If the user assumes the role after you revoked the permissions, then the deny policy does not apply to that user." So stage-1 step 1 alone does not stop an attacker with a still-valid Vercel OIDC token; step 2 (trust policy / provider removal) or step 3 (DisableKey) is what actually stops re-assumption. The dossier's ordering already includes them; keep DisableKey as the primary kill switch. CloudTrail: KMS events are management events, first S3 copy free, $2.00/100,000 for extra copies, 90-day event history, and a per-trail switch can EXCLUDE all kms.amazonaws.com events (must not be set).

## Things the analyst missed (or that changed recently)

1. AWS IAM "shared OIDC provider" controls (IAM doc history: 2025-06-06 and 2025-08-01; https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_oidc_secure-by-default.html). IAM now classifies "Vercel global endpoint https://oidc.vercel.com" as a SHARED provider and requires the role trust policy to evaluate `oidc.vercel.com:aud`; role creation or trust-policy updates without it fail with MalformedPolicyDocument. The Team issuer (`https://oidc.vercel.com/<team>`) is a private provider with no mandatory claim. So: use Team issuer mode (Vercel also marks it "Recommended"), and if a project is still in Global mode (older default) the trust policy must keep an aud condition (and sub). Not mentioned in the dossier. It strengthens, not weakens, the recommendation.
2. Vercel Deployment Policies (https://vercel.com/docs/deployments/deployment-policy, last_updated 2026-07-14): per-environment rules restricting which Git orgs/repos and which deployment mechanisms (Git, CLI, Deploy Hooks) can deploy to Production. This directly reduces the "anyone who can execute code in the production project" blast radius and is not in the dossier's hardening list.
3. Direct `kms:Encrypt`/`Decrypt` for values <= 4,096 bytes (API_Encrypt.html: "Encrypts plaintext of up to 4,096 bytes"; SYMMETRIC_DEFAULT: 4096 bytes). The dossier lists the limit in its findings table but never evaluates the simpler design: for API keys/tokens under 4 KB, one Encrypt per write and one Decrypt per reveal costs the same number of KMS requests as GenerateDataKey + Decrypt, removes all local crypto (no nonce, AAD canonicalisation, plaintext-DEK handling), keeps context/policy/ReEncrypt semantics, and still leaves envelope for larger blobs. Trade-off: plaintext transits to KMS (TLS), hard 4 KB ceiling, and no local AAD beyond the KMS context. Worth an explicit decision.
4. Custom audience for the AWS exchange: Vercel docs (oidc/aws "Custom audience") and the provider (`audience`, `jti`, `skipTokenCache`, `durationSeconds`) allow a dedicated `aud` (e.g. `sts.amazonaws.com` or a Mosshatch-specific value) which must also be added to the IAM provider's Audiences. It is an inexpensive way to make the prod role's aud distinct from what other Vercel-issued tokens carry.
5. AWS-side network pinning is possible: Vercel Static IPs (Pro/Enterprise, $100/month per project plus Private Data Transfer, project-wide not per environment, https://vercel.com/kb/guide/can-i-get-a-fixed-ip-address, updated 2026-09-28) could support an `aws:SourceIp` condition on the role/key policy so stolen STS credentials cannot be replayed from elsewhere; cost dwarfs KMS spend, so it is an option, not a default.
6. Vercel Connect (https://vercel.com/docs/connect, updated 2026-09-18) is a new team-level credential broker for agents ("without storing provider keys"); not a KEK substitute, but adjacent to the "agents get scoped credentials" product surface and worth a look in the agent-token design.
7. NIST revision detail (tags < 96 bits to be removed; wGCM) - no effect, but the 2^32 statement is still from the 2007 text.
8. AWS KMS and IAM doc histories show no 2026 change to pricing, quotas, encryption-context semantics or rotation rules (KMS latest entry 2026-03-06 service-principal grants; IAM latest OIDC-related entry 2026-05-12 GitHub job_workflow_ref).
