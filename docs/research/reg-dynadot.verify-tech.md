## Verdicts

### Coverage rows (REST v2 command feed, per-command specs)

1. **register (idempotency / duplicates): CONFIRMED.** `POST /restful/v2/domains/{domain_name}/register`, signature required, sandbox true. Request: `domain{duration REQ, privacy REQ (off|partial|full), contacts, customer_id, name_server_list}`, `currency`, `register_premium`, `coupon_code`. Response params: only `domain_name`, `expiration_date` (no order id). Error list: 409 "The domain is already owned by your account and cannot be purchased again."; 409 "The domain is not available"; 500 "Domain requires further investigation: order created [order_id]."; 400 ".AI domains require a minimum registration period of 2 years for new registrations."; 402 "Insufficient funds."; 502/503 registry errors. `grep -i idempot` on the whole 2 MB feed returns 0 hits. X-Request-ID is described only as tracking/correlation. NEW: `register` also lists 429 "Daily quota for the command has been reached. Please try again tomorrow." (only `search`, `domain_appraisal`, `register` carry it) so the register call has a daily quota whose size is not documented anywhere I found. Also register/transfer_in list 400 "The domain is not supported by your account type."
2. **renew: CONFIRMED.** `year` REQ ("current expiration year"), 400 "Expiration year does not match.", 400 "There is another command processing for {parameter}", 409 "Order exists already.", 403 "This domain cant renew yet.", 409 "The domain requires late renew fee, renew cancelled." (from `no_renew_if_late_renew_fee_needed`). The double-renew guard is the analyst's inference from the year check; the docs do not call it an idempotency mechanism.
3. **startTransferIn: CONFIRMED.** `POST .../transfer_in`, `duration` must be 1 (400), `privacy` REQ, 409 "There is already a transfer request in progress for the domain [domain_name].", 409 "Order exists already.", 402 funds. Response demo is `{code:200,message:Success}` with no data; a 202 "Accepted" response is also documented (analyst did not mention 202). No order id in the REST response params.
4. **getTransfer: CONFIRMED with nuance.** `GET .../transfer_status?transfer_type=transfer_in|transfer_away` returns `domain_transfer_status_list[{order_id, transfer_status, failed_reason, expiration_date, order_created_date, order_completed_date}]`; no signature needed. The only `transfer_status` value shown in the feed is "Transferred" in the demo; there is no enumeration, so "vocabulary undocumented" holds. `GET /orders/{order_id}` (`order_get_status`) returns `order_status` plus item statuses with a long example list (e.g. Transferred, Transferred Away, Not Transfered, Failed, Cancelled). `POST /orders/{order_id}/update_transfer_auth_code` and `/cancel_transfer` exist (409 "The domain transfer has already started." / "can not be cancelled, transfer status: [transfer_status]"). Legacy `get_transfer_status` text: 'none'/'approved' cancellable, 'waiting' started, 'auth code needed' bad code (api-commands, line 1886).
5. **getAuthCode: CONFIRMED (partly legacy-sourced).** `GET .../transfer_auth_code?new_code&unlock_domain_for_transfer`, signature required. 409s: "The [domain_name] is disabled.", "was UDRP locked.", "Domain expired or expiring, please renew the domain first.", "The domain has the 60-day transfer lock.", "The domain is in user auction."; 404 "The domain is non-auth"; 400 "The domain does not need auth code to transfer". The "requires api skip lock agreement" and "unlock domain and account first" statements are in the LEGACY doc ("unlock_domain_for_transfer (Optional. Requires api skip lock agreement to use)"; "You must unlock your domain and account before requesting auth code."). The REST v2 feed only ties the skip-lock agreement to `set_domain_lock_status`. What v2 returns for a locked domain is therefore undocumented.
6. **setLock: CONFIRMED.** `PUT .../domain_lock {lock: bool}` (`set_domain_lock_status`). 409s include "Unlock domain feature requires api skip lock agreement, you can enable or disable this in the control panel.", auction lock (usually 18 days), buy lock (about 30 days), installment lock, Afternic/Sedo hold, user auction. Account lock is a separate `set_account_lock_status` (v2 only).
7. **startTransferOut: CONFIRMED.** No initiate command exists in either feed. `POST /orders/{order_id}/authorize_transfer_away {domain_name, approve}`; webhook `domain_transfer_away` payload `{domain, gaining_registrar, order_id}`; help page: "a transfer away order will be created and the 'Transfer Away' email will be sent to you" and "may take some time for our system to be notified"; prep step "domain is older than 60 days". 409 "Invalid order status." / "Domain can not approve transfer out." No fee or default-approval timing stated by Dynadot (ICANN 5-day default not re-verified in this lens).
8. **DNS CRUD: CONFIRMED.** `GET/POST/DELETE /domains/{d}/records`. Parsed the record-type tables from the feed: main list a, aaaa, cname, aname, caa, txt, forward, stealth, mx, email (srv and ns "Not supported for main DNS"); sub list a, aaaa, cname, caa, txt, forward, mx, email, srv, stealth, ns (aname "Not supported for sub DNS"). `set_dns`: main max 20, sub max 100, `ttl` default 86400 (single TTL), `add_dns_to_current_setting` default false (so default replaces). Response params carry no record id field. `remove_dns`: signature not required; body type+value. 409 "Cannot set DNS ... existing Email Settings"; 429 "Cannot add DNS ... reached the upper limit". CNAME on the apex conflicts with a, aaaa, aname, caa, forward, stealth, email, mx, txt (per table).
9. **getDomain and registry status codes: CONFIRMED.** `GET /domains/{d}` returns `locked, disabled, udrp_locked, registrant_unverified, hold ("Client/Registrar Hold Status"), privacy, renew_option, transfer_lock_end_date, status` plus contact ids and glue_info. `status` is a free-text Dynadot vocabulary ("active, deleted grace, transferaway, expired, moved (pull), deleted by cust, ..."). 0 hits in the whole feed for clientTransferProhibited, pendingDelete, redemptionPeriod, serverHold, "EPP". The status list has no explicit redemption or pending-delete value.
10. **checkAvailability caps: CONFIRMED.** bulk_search `domain_name_list` doc text: "Regular - 5, Bulk - 10, Super Bulk - 20"; 400 "Too many domains entered, the current price level permits a maximum of [count] domains per request." `source` (registry|cache) and `confidence` (high|low) are returned only when `timeout` is given. Legacy `search`: "regular account can specify 1 domain per command, bulk and super bulk account can specify up to 100 domains" (domain0..domain99). `power_search` (URL `.../power_search_new`) 401 "This API is only available for specific accounts."
11. **quote: CONFIRMED.** bulk_search/search with `show_price` gives `price_list[{registration_price, renewal_price, transfer_price, restore_price}]`; catalogue `GET /domains/get_tld_price` returns `price_level`, `all_years_register_price`, `all_years_renew_price`, `min_duration`, `max_duration`, `delete_grace_fee`, `delete_grace_max_rate`, `delete_grace_current_rate`. REST renew has no price_check; legacy renew has `price_check`.

### Sandbox and credentials: CONFIRMED
- Docs "Sandbox" section: Dynadot account, API settings page, "Generate your API Sandbox Key and API Sandbox Secret Key", "allow some time for the system to activate your sandbox keys and create your Sandbox account", pre-funded "10,000 in all supported currencies", base URL `https://api-sandbox.dynadot.com`, "Certain commands may differ from Production, and the Sandbox cannot fully simulate all possible complex scenarios."
- Help page find-API-settings (updated 2026/03/10): Tools > API, unlock account, production and sandbox keys displayed; Secret Key and Sandbox Secret Key for X-Signature; IP allow-list single IP or CIDR; "allow at least 10 minutes".
- Feed: every adapter-relevant command has `supportApiSandbox: true`; all 11 webhook events `supportApiSandbox: "false"`; aftermarket, CNNIC privacy, site builder, email hosting commands false.
- Nothing states that sandbox keys need a reseller account or that transfers/expiry/DNS resolution are simulated: UNVERIFIABLE without an account.
- Probes (no credentials): with `Accept: application/json`, prod v2 and sandbox v2 with no Authorization: HTTP 200 text/plain body `{"code":400,... "The Authorization header not entered"}`; bad bearer on v2: real HTTP 401 JSON. Same body-code pattern on v1 but bad bearer returns HTTP 200 with body `{"code":401,... "Invalid key"}`.

### Rate limits: CONFIRMED
- Docs "Rate Limiting": "Only 1 request can be processed at a time"; Regular 1 thread 60/min (1/sec); Bulk 5 threads 600/min (10/sec); Super Bulk 35 threads 6000/min (100/sec). Concurrency 429 text: "You have reached the maximum allowed requests within the concurrent limit of your account. Please try again later." Per-command error lists instead say "Too many requests. Rate limit exceeded. Please try again after 60 seconds." (two different 429 texts).
- Legacy doc table also lists "premium bulk 25 threads 6000/min".
- Bulk searches per day 1,000/2,000/5,000 (prices page and Jan-2025 blog). Appraisals: docs 50/100/300 per day vs prices page and blog 10/100/1,000: discrepancy confirmed.
- Spend thresholds $500 and $5,000 per 365 days (bulk-pricing help); Super Bulk gets "Prioritized API Calls" and a dedicated account manager.
- Docs also state "bulk creations, updates, deletes are not supported, and each of those request type is limited to one object or action" (REST).

### Docs changelog / deprecations
- v2 changelog has exactly one entry, October 9, 2025: sandbox live; X-Signature mandatory for sensitive commands; optional machine-readable docs; "Search Access Restricted"; "Reseller account no longer required to enter at least 1 IP to use API(RESTful API only)"; mandatory paging parameters (get_listings). The same entry is what the V1 selector view shows too. No deprecation notice found anywhere in the REST docs, the legacy docs or the help pages I read.
- Beta banner (v2): "This API documentation is Beta. Endpoints, fields, error codes, and behaviors may change without notice and backward compatibility is not guaranteed. Avoid relying on it for critical production workflows." CONFIRMED verbatim.

### Other claims
- **Prepaid balance only / 402: CONFIRMED with a caveat.** Prepay minimum "$5 USD", "non-refundable"; auto prepay "only ... available when your Dynadot account is at least one year old and has an order history"; WHMCS listing: "all registrations, transfers, and renewals are billed against your Dynadot balance"; 402 "Insufficient funds." on register/renew/transfer_in. Caveat: the feed also defines a webhook `order_payment_required` whose payload has `payment_method` (credit card, paypal, account balance, bank wire ...) and status "Waiting for Payment", so orders in a waiting-for-payment state exist somewhere in the platform; whether API orders can ever land in that state is not documented.
- **Webhooks: CONFIRMED.** 11 events (order_completed, domain_transfer_away, domain_expiring, account_balance_reminder, whois_verification_required, whois_verification_notification, order_payment_required, domain_status_changed, domain_suspension_status_changed, maintenance_notice, contact_kyc_status_changed); receiver replies `{"Status":"200"}`; grep of the docs for retry/backoff/attempt/redeliver: nothing. `verify_link`: "Not returned for reseller accounts."
- **X-Signature: CONFIRMED.** String to sign = apiKey + "\n" + fullPathAndQuery + "\n" + xRequestId + "\n" + body, HMAC-SHA256 with the secret, Base64; no timestamp (replayable). `requireSignature` false for search, bulk_search, get_tld_price, get_transfer_status, remove_dns, and get_nameserver (all six verified in the feed).
- **IP block returns 403: CORRECTED.** The message "The request is not allowed from the current IP address" appears only in the error lists of three CNNIC-privacy commands (create/set/remove_cnnic_privacy); the general docs list 403 only generically. Enforcement for other commands is undocumented.
- **No public status page: CONFIRMED.** https://status.dynadot.com returns HTTP 200, 0 bytes.
- **Sale 'Reseller' access to aftermarket: N/A to adapter**, but feed confirms several aftermarket commands return 403 "The feature is currently not available to reseller accounts." and one auction error says "The auction type is not supported for the reseller program."
- **API-use clauses: CONFIRMED verbatim** in Dynadot ToU s13.1(b)(c) and GDG ToU s12.1(b)(c); both version date 2026-08-18. Reseller Agreement version date 2023-08-15.
- **WHMCS module: CONFIRMED** (updated 9 Sep 2026, 13 reviews, 4x5 star, 2x4 star, 7x1 star; v2.0.0 review 2026-07-28 "Invalid JSON format", Dynadot reply that a fix is deployed).
- **Lifecycle window conflict: CONFIRMED.** TLD pages 30-day restore; renewal-grace help example: 30 days grace (05-01 to 05-31), redemption 05-31 to 07-10 (40 days), pending delete 07-10 to 07-15; ToU s8.2 Post-Expiration 40 days, s8.8 Deletion Period 30 days, s8.4 auction within first 30 days, s8.6 no transfer in last 10 days of Post-Expiration, s8.11 transfer within 45 days of expiry loses 1 year.

## Items the analyst missed (see structured output)
1. REST v1.0.0 exists (103 commands, `/restful/v1/...`, not labelled Beta, live on prod and sandbox), without remove_dns, get/set_nameserver, set_account_lock_status, post_grace_delete, power_search, domain_appraisal, and with no per-command error catalogue in its feed.
2. `Accept: */*` (curl/HTTP-library default) is rejected: HTTP 200 body `{"code":400,... "Unsupported accept value in the header."}`; clients must send Accept: application/json or application/xml.
3. `register` and single `search` carry an undocumented-size daily quota (429), in addition to the 1,000/day bulk-search figure.
4. GDG roster page claims prices are "listed at cost, straight from the registries" but shows no prices; a separate GDG wholesale price list may exist and would differ from the Dynadot Reseller tab.
5. Reseller-tab .dev/.app registration is above the retail non-promo list price, and Reseller tab equals Regular for the other four TLDs: no evidence of any wholesale discount.
6. `.com` and `.ai` grace-delete current rates (7.75%, 8.74%) sit close to the 10% cap, so the wait-list path is realistic for those two.
7. `order_payment_required` webhook / "Waiting for Payment" state contradicts a pure "402 or success" model.
8. Docs feed gives 202 Accepted for transfer_in; a client must treat 200 and 202 as success.
9. The 429 text differs between the overview (concurrency) and per-command lists ("try again after 60 seconds").
10. Google Registry names (app, dev, page, how, new, day, zip, mov, foo ...) are systematically absent from the API-supported list, which suggests a platform-level rather than a one-off omission.
