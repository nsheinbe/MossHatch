# Registrar dossier: NameSilo (NameSilo, LLC, IANA Registrar ID 1479) - REST/GET API v1

Prepared for the Mosshatch Phase 0 plan. Research date and access date for every source below: **2026-09-29**. All prices USD. Nothing here was answered from memory; anything that could not be verified is marked **unverified** and listed in section 11.

## TL;DR

1. **Resale: conditional yes, but the contract is not public.** NameSilo's own FAQ says anyone can become a reseller with "no special sign up": create an account, open the Reseller Manager page and accept "our reseller terms and conditions". Those reseller terms sit behind login and could not be read, so the governing clause on resale, price changes and suspension is **unverified**. The public Registration Agreement has no reseller clause; it makes the account holder (Mosshatch) warrant "the authority to bind" the end customer.
2. **No wholesale price.** "There is no special pricing for resellers." The only lever is the free Discount Program (account funds only, $50 minimum per top-up, no coupons). Its starter tier is near cost for .com ($11.05 register and renew) but thin for the others; promo first-year prices then jump (.io 38.99 -> 69.89, .studio 17.89 -> 40.89). Restore/redemption fee: not published anywhere I could reach.
3. **API is complete for the happy path but crude for a multi-tenant reseller**: every call is an HTTP GET with the account-wide API key in the query string; no idempotency key, no webhooks, no rate limits published, DNS has no upsert (record ids change on update), and `retrieveAuthCode` only emails the code to the administrative contact.
4. **Duplicate and retry behaviour is undocumented.** The response-code table has 262 ("already active within our system") and 400 ("Existing API request is still processing"), and NameSilo says it monitors "multiple attempts of the same operation for the same domain" as a batch-abuse signal. Blind retries of register or renew are unsafe (renew would double-charge).
5. **Sandbox exists but is by request only** ("please contact us"); host `sandbox.namesilo.com/api` answers like production. What it simulates is unverified.
6. **Lifecycle traps**: 3-day (not 5-day) cancel-for-refund window, cancellations only in the web UI; expired domains lose DNS to a parking page on day 1 and are removed from your account and auctioned on days 31-40; `renewDomain` silently performs a paid restoration in the redemption period; refunds, outbound-transfer approval and cancellation have no API.
7. **Red flags**: one account holds every customer's domains and NameSilo may "terminate or suspend all Services provided through your Account" over one domain; 30-day no-cause termination; "reasonable efforts" 30 days' notice of fee changes; API key cannot be retrieved after creation; status page unreachable from this environment; a 2022 copyright suit names NameSilo's free privacy service.
8. **Recommendation: FALLBACK** (weak). Cheap and self-serve for .com/.dev/.app, but read the in-account reseller terms and get written answers on rate limits, sandbox scope and restore fees before wiring it in. Do not make it primary.

## 4. RATE LIMITS and operational constraints

### 4.1 Limits
- **No numeric limit is published.** I searched every fetched API and support page for rate limit, per second, per minute, throttle and concurrent: no hits. No rate-limit headers appeared on the (unauthenticated) error responses I probed.
- **Two lanes, policed by monitoring.** https://www.namesilo.com/support/v2/articles/account-options/api-automated-batch: "Standard API use ... any API call that was directly triggered by a human action. Batch API use occurs when software programs make automated and often times repetitive API calls." "Batch use must ONLY use /apibatch for all API calls. The batch API supports all standard API calls and works exactly the same". Violations: "We closely monitor API use and proactively limit batch use in /api ... batch processing calls to /api will be stopped in near real-time ... will in all likelihood result in API and/or account suspension." Signals monitored: "Multiple repeated API calls (e.g., multiple attempts of the same operation for the same domain such as multiple transactions for creating domain names)" and "A high ratio of 'unsuccessful' to 'successful' API responses".
- **Mapping for Mosshatch (inference):** human passkey-approved purchases are "standard" (`/api`); availability sweeps, renewal cron jobs, DNS syncs and agent-initiated polling are "batch" (`/apibatch`). Ask NameSilo in writing where an AI-agent-initiated call falls.
- **IP allow-list:** "Users can enter up to 5 IP addresses to limit authorized originating API connections ... All fields can be left blank to allow connections from all IP addresses." (API Manager). Code 113 "This API account cannot be accessed from your IP". Vercel functions have no fixed egress IPs by default; Static IPs are a paid Pro add-on ($100/month per project per `tech-vercel-platform.md`, citing https://vercel.com/docs/networking/static-ips). So either leave the list empty (the key is then the only control) or pay for static egress.

### 4.2 Auth, formats, errors
- **Auth:** one API key per account, passed in the query string. Code 120 "API key must be passed as a GET". API Manager: "There is no way to retrieve an already issued API key. In the event the API key is forgotten, the only option is to generate a new key." Sub-accounts cannot use the API (code 112). No scopes, no per-operation permissions, no per-customer keys. Consequence: the key appears in every URL, so do not log outbound URLs; treat it as a full-account credential.
- **Transport:** "All operations *MUST* be invoked via GET method"; "All requests to the API must utilize https". Observed: `http://` gets a Cloudflare 301 to https (the key would already be on the wire in clear); a POST returns **HTTP 200** with `{"reply":{"code":210,"detail":"No route found for \"POST http://www.namesilo.com/api/v1/getPrices\": Method Not Allowed (Allow: GET)"}}`.
- **Formats:** `type=xml` or `type=json`; envelope `{"request":{"operation","ip"},"reply":{"code","detail",...}}`; success is `code` 300.
- **HTTP status is not a reliable signal.** With a dummy key I saw 401 + envelope (code 110), 400 with a plain-text "Invalid Request: invalid key" for an unknown operation, and 200 + envelope error code 210 for a POST. Always branch on `reply.code`.
- **Code table (bundle chunk 2591, selected):** 101 HTTPS not used; 108 missing parameters; 110 invalid key; 113 IP not allowed; 115 "Central Registry Not Responding - try again later"; 116 invalid sandbox account; 119 "Insufficient account funds"; 200 "Domain is not active, or does not belong to this user"; 201 internal error; 210 general error; 250-256 already-in-state no-ops; 261 "Domain processing error"; **262 "This domain is already active within our system and therefore cannot be processed."**; 263 invalid years; 264 cannot renew; 265 "Domain cannot be transferred at this time"; 266 no transfer exists; 267 invalid domain / unsupported TLD; 280 DNS modification error; 300 success; 301 registered but NameSilo nameservers used; 302 order succeeded but default contact used; **400 "Existing API request is still processing - request will need to be re-submitted"**.
- **Batch limits:** availability 200 domains per call; transfer availability 200; `changeNameServers` 200 domains; portfolio associate 200; registration `years` 1-10; up to 13 nameservers.
- **Funding constraint:** purchases draw on a prepaid balance or a verified card. Top-ups are `addAccountFunds` from a stored verified card; no auto-top-up is documented, so monitor `getAccountBalance` (code 119 on shortfall).

### 4.3 Making a register call safely retryable (Mosshatch-side design; NameSilo offers no idempotency key)
1. Write an intent row (`customer`, `domain`, `years`, `expected order_amount`, your own idempotency key) before the call. Serialise to one in-flight call per domain (code 400 says the earlier request is "still processing").
2. Disable automatic HTTP-client retries for `registerDomain`, `renewDomain`, `transferDomain` and `addAccountFunds`. All are GETs, and many HTTP stacks retry GETs on network errors.
3. Treat a timeout, HTTP 5xx, code 115, 201, 210, 261 or 400 as **unknown outcome**. Resolve by reading: `getDomainInfo` (code 300 = it exists; compare `created`/`expires`), then `listOrders` from just before the attempt and `orderDetails` (status "Processed" and amount). Only re-send if the domain is absent and no matching order exists.
4. Treat code 262 as "someone owns it in NameSilo's system", which may be your own earlier attempt: confirm with `getDomainInfo` (code 200 means it is not in your account). Inference: 262 is the likely reply to a re-sent register after success, but NameSilo does not say so.
5. For `renewDomain`, record the expected new `expires` first; after an unknown outcome, read `getDomainInfo` and only re-send if `expires` did not move. NameSilo's own auto-renew (default on, section 6) can race a Mosshatch renew job; either set `auto_renew=0` at registration or check `expires` immediately before every renew.
6. Keep retries rare and log them: repeated same-domain transactions are one of NameSilo's abuse signals (4.1).
7. Reconcile nightly: `listOrders` against Mosshatch's own ledger.

- **Cost-basis reading (derived, not from NameSilo):** using the registry wholesale in `tld-registry-facts.md` ($10.26 + $0.20 ICANN for .com), NameSilo's .com DP price of $11.05 is roughly $0.59 above cost, while .ai (94.99 vs about 80), .io (69.89 vs about 50 renewal), .dev/.app (14.89/16.89 vs about 12.20/14.20) and .studio (40.89 vs about 31.20) carry larger spreads. ## 7. WHOIS PRIVACY and RDAP redaction

- **Free, unlimited, provider PrivacyGuardian.org.** "We are proud to offer FREE WHOIS Privacy Protection for all of our domain holders without limitation!" "Partnering with PrivacyGuardian.org ..." (https://www.namesilo.com/support/v2/articles/domain-manager/whois-privacy). Pricing page: "Free WHOIS Privacy Forever".
- **Default on? Not through the API.** `registerDomain` and `transferDomain`: `private` "If not supplied, the domain will be registered without privacy" / "configured without privacy". Mosshatch must send `private=1` explicitly (or call `addPrivacy`). Whether new web-UI registrations default to private was not verified.
- **Controllable via API:** yes: `addPrivacy`, `removePrivacy`, and `private` at registration. Exclusions: ".us, .in or .tickets"; ".ca domains cannot use privacy".
- **Terms that bite:** NameSilo may "suspend, terminate and/or disclose your personal information" for breach, legal process, or if continuing "places us in any jeopardy"; "It is your responsibility to reply to any such communication within three (3) days", otherwise NameSilo "reserve[s] the right to immediately release your contact information and to suspend or terminate the WHOIS privacy service". Mosshatch must relay these within 3 days.
- **Contacts stay on file.** "The information you submit related to the various domain roles (registrant, administrative, technical and billing) will remain associated with the domain at all times." Privacy changes only what public lookups show.
- **RDAP.** NameSilo runs `https://rdap.namesilo.com/domain/{name}` (IANA lists it for registrar 1479; I queried `NAMESILO.COM`: `rdapConformance` includes `icann_rdap_response_profile_1` and `redacted`; `port43` is still `whois.namesilo.com`). The record for NameSilo's own domain shows a company contact, so it does not demonstrate redaction of a customer's data. The RDAP terms forbid bulk use: "Do not, under any circumstance, access this RDAP Domain Database using any high volume, automated, electronic processes" and storing results ("may not store results in memory, databases, on a hard disk"). Mosshatch should read domain status from its own state, `getDomainInfo`, and registry RDAP, not by scraping NameSilo RDAP. Whether personal data is redacted for non-private domains in NameSilo's RDAP was not verified with a customer domain.

## 10. RECOMMENDATION: FALLBACK (weak; not primary, not reject)

NameSilo is a workable low-cost **fallback**, not a primary reseller backend for Mosshatch. For it: resale through the API under a reseller's own brand is openly invited and self-serve with no application, KYC or volume commitment; the API is free and covers register, renew, lock, DNS CRUD, transfer-in and privacy; private-labelling of the mandatory emails is included; WHOIS privacy is free; and the Discount Program's starter tier puts .com at $11.05, close to registry cost. Against it: the one document that decides whether Mosshatch's model is permitted (the in-account reseller terms) is unreadable in advance, so the legal gate is unverified; there is no reseller price list and promo-then-jump pricing on .dev/.io/.app/.studio breaks a simple "wholesale plus flat fee" promise; the API has no idempotency key, no webhooks, no published limits, GET-only state changes with the account key in the URL, and a batch-abuse monitor that treats repeated same-domain calls as suspicious, which collides with safe retry; auth codes are emailed rather than returned and outbound transfers, refunds and cancellations are UI-only, which conflicts with the human-passkey-approves-money model for anything Mosshatch cannot drive by API; the expiry policy auctions lapsed domains after 30 days; and a single-account architecture lets one problem domain suspend every customer. If NameSilo is kept as the cheap second adapter, restrict it to .com, .dev and .app first, get written answers before integration (reseller terms text; rate limits and where agent traffic sits between `/api` and `/apibatch`; sandbox scope; restore fee per TLD; .ai year handling; whether DP prices apply to API orders), enable "reject orders with invalid contact information" and disable the renewDomain-restores override, and build the retry protocol in section 4.3.
