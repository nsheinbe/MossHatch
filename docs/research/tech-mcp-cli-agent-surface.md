# MossHatch Phase 0 research: agent-facing surface (MCP + REST + CLI) and its authentication

## TL;DR

1. Current MCP spec is **2026-07-28** (stateless: no `initialize`, no `Mcp-Session-Id`, POST-only Streamable HTTP, server-initiated elicitation replaced by "input_required" round trips); DCR is deprecated in favour of Client ID Metadata Documents; OAuth 2.1 + RFC 9728 metadata + RFC 8707 `resource` remain the auth model [F1-F3, F5, F8-F10].
2. Use TypeScript SDK **v2** (`@modelcontextprotocol/server` 2.2.0, published 2026-09-28); npm `@modelcontextprotocol/sdk` 1.31.0 is still tagged `latest` but tops out at protocol 2025-11-25 [F19, F20, F73]. `createMcpHandler(factory)` gives a stateless `{fetch}` that maps onto a Vercel `/api` function, but it performs **no** auth/Origin checks; I confirmed that locally [F21, F22, F25].
3. Client reality: Claude Code, Cursor and VS Code accept a static `Authorization: Bearer` header; claude.ai/Desktop custom connectors need OAuth (static headers are a beta for a limited set of orgs) [F29, F34, F35, F37, F38, F74]. Phase 0 = scoped static `mh_` tokens + device-flow CLI login; OAuth AS (CIMD + DCR fallback) in Phase 1.
4. "Needs human approval" must be **server-enforced** (a `pending_approval` result + first-party passkey page). Elicitation is not a control: Claude Code lets an `Elicitation` hook auto-answer, legacy (2025-era) clients on a stateless server cannot receive it (tested), and clients without the capability get `-32021` (tested) [F24, F32].
5. Annotations change client behaviour: VS Code (and Anthropic's directory rules for Claude) skip confirmation for `readOnlyHint` tools, so **never** mark anything that returns secret values read-only [F36, F38].
6. CLI login = RFC 8628 device flow (Vercel and gh precedent); device-code phishing is real (Storm-2372), so the approval page must show device/IP/time, require a passkey, and use short code lifetimes [F45-F50].
7. `mosshatch run`: env-only, denylist of dangerous names (LD_PRELOAD, NODE_OPTIONS...), propagate the child's exit code (128+n on signal), never take tokens on argv, mask output; store the refresh token with `@napi-rs/keyring` (keytar last released 2022) and fall back loudly, not silently [F50-F56, F58].
8. Tokens: `mh_<kind>_<32 base62>+<CRC32>` for GitHub secret-scanning detection; SHA-256 at rest is adequate for >=128-bit random tokens (NIST-based inference); only GitHub's **partner program** (email secret-scanning@github.com) detects leaks in other people's repos, custom patterns do not [F59-F61, F63].
9. Rate-limit per token id, not IP: Vercel WAF header keys are Enterprise-only and all claude.ai connector traffic shares 160.79.104.0/21 [F27, F28].
10. Biggest gaps: 2026-07-28 support in Cursor/VS Code/claude.ai is undocumented; nothing was deployed to Vercel; GitHub HTML pages and w3.org were unreachable (Section 12).

Scope and method: access date for every source is **2026-09-29**; topic = MCP server, REST, CLI and tokens; no application code was written, and a few throwaway experiments ran only in the research scratch directory (Appendix B).

Citation convention: **[F#]** points to the Findings Register (Appendix A) which carries URL, access date 2026-09-29, confidence and a short exact quote (markup stripped). Text tagged **(analysis)** is my recommendation or inference, not a sourced fact.

## 1. MCP specification state (2026-07-28)

| Topic | What the current spec says | Consequence for MossHatch |
|---|---|---|
| Revision | 2026-07-28 is "Current" [F1]. Previous: 2025-11-25. | Target 2026-07-28, keep serving 2025-era clients. |
| Lifecycle | No `initialize`; every request carries protocol version + client capabilities in `_meta`; clients SHOULD send `clientInfo`; `server/discover` is mandatory [F2]. | Stateless functions are now spec-native. `clientInfo` is client-declared: log it, never authorize on it (analysis). |
| Transport | Single POST endpoint; JSON or per-request SSE; GET/DELETE -> 405; no resumability; required headers `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` [F3]. | One route `/mcp`. No long-lived streams needed unless `subscriptions/listen` is offered (avoid; Vercel function duration caps [F80]). |
| Origin | Servers MUST validate `Origin` (403 if invalid) [F4]. | Add allowlist check in front of the SDK handler. |
| Server->client asks | Replaced by MRTR `input_required` results; `requestState` is attacker-controlled [F5, F6]. | Design approvals without depending on it (Section 4). |
| Authorization | Optional; HTTP SHOULD follow it; stdio reads credentials from env [F7]. Servers MUST publish RFC 9728 PRM [F8]; clients MUST send RFC 8707 `resource`, servers MUST validate audience and not pass tokens through [F9]. | Static bearer tokens are permitted in practice; OAuth needed for hosted Claude apps (Section 3). |
| Registration | Pre-registered > CIMD > DCR; **DCR deprecated** (earliest removal: first revision released on or after 2027-07-28) [F10, F92]. | Build CIMD support first, DCR as fallback because clients still use it (Section 3). |
| Tokens | Header only, never query string [F11]; short-lived; refresh rotation for public clients [F93]. | See Section 8. |
| Scope step-up | 403 + `WWW-Authenticate: error="insufficient_scope", scope="..."` [F12]. | Use for OAuth clients; static-token clients need a readable tool error too (analysis). |
| Tools | `tools/list` MAY vary by the token's authorization [F13]; servers MUST validate inputs, enforce access control, rate limit, sanitize outputs; human in the loop SHOULD exist [F13]. | Per-token tool visibility is allowed: hide tools the token cannot use. |
| Caching | `ttlMs` + `cacheScope` required on list results [F14]. | Keep `cacheScope: private`; SDK default observed: `ttlMs 0`, `private`. |
| Annotations | Hints only; untrusted unless server trusted [F15]. | Treat as UX, not security (Section 5). |
| Elicitation | No secrets/payment credentials in form mode; URL mode for sensitive flows; `accept` != done; verify identity of URL opener; no pre-authenticated URLs [F16]. | Secret entry and approvals happen on a first-party page. |
| Tasks | Official extension with `input_required`; approvals named as a use case; not in the client-support matrix [F17]. | Watch, do not depend on it. |
| Draft standards | OAuth 2.1 (spec cites draft-13, IETF has rev 16) [F18], CIMD (spec cites draft-00, IETF has rev 02) [F90]. | Expect drift; pin behaviours to tested clients. |

## 2. Hosting a stateless MCP endpoint on Vercel

- **Package**: `@modelcontextprotocol/server@2.x` (Node >=20) with `zod@4`; not `@modelcontextprotocol/sdk` [F19, F20, F26, F73]. v2 went 2.0.0 (2026-07-27) -> 2.2.0 (2026-09-28) in two months [F73], so pin exact versions and read release notes on upgrade (analysis).
- **Handler shape**: `createMcpHandler(factory)` returns `{ fetch, close, notify, bus }`; the factory runs on every request and receives `{ era, authInfo, requestInfo }`; keep it cheap and create pools at module scope [F21]. Vercel `/api` files may `export default { fetch(request) {...} }` [F25], so an `/api/mcp` file can call auth gate -> `handler.fetch(request, { authInfo })`. Vercel presents `mcp-handler` v2 for Next.js App Router routes [F26]; it is optional here because `createMcpHandler` already yields a fetch handler (analysis).
- **You must add**: bearer verification and Origin/Host validation. Confirmed locally that a request with `Origin: https://evil.example` returns 200 from the bare handler [F22]. The SDK ships `requireBearerAuth`, `requireScopes`, per-tool `scopeChallenge`, `originValidationResponse`, `hostHeaderValidationResponse`, `oauthMetadataResponse` [F22, F23].
- **Verified locally with a SHA-256-hash-lookup verifier**: no token -> 401 `invalid_token` with `WWW-Authenticate: Bearer ... resource_metadata="..."`; valid token reaches tools with `ctx.http.authInfo`; a tool guarded by `requireScopes('secrets:reveal')` returns 403 `insufficient_scope` with `scope="secrets:reveal"` [F23, Appendix B]. `AuthInfo.expiresAt` must be set or the gate returns 401 [F23].
- **Legacy clients**: default `legacy: 'stateless'` serves 2025-era clients per request; their GET/DELETE get 405 [F21]. Do not set `legacy: 'reject'` until the clients you care about are known to speak 2026-07-28 (only Claude Code's v2 runtime is documented to) [F31].
- **Limits**: Node functions default to 300 s (Hobby/Pro), Pro max 800 s, 4.5 MB request/response cap [F80]; Claude Code warns above 10k tokens of tool output and caps at 25k [F70], so paginate list tools.
- **Not tested**: an actual Vercel deployment, `/.well-known/*` rewrites, and streaming behaviour on Vercel (Section 12).

### 3.2 What this means

1. **Phase 0 auth** = static scoped bearer tokens (`mh_pat_...`) accepted on both REST and `/mcp`; this reaches Claude Code, Cursor, VS Code and stdio-only clients through `mcp-remote` (analysis from the matrix).
2. **Hosted Claude apps need OAuth** for per-user connectors; the static-header path is beta and org-wide, so it cannot represent an individual's passkey identity [F34, F35].
3. The OAuth AS MossHatch would need (Phase 1): RFC 8414 metadata, `authorization_code` + PKCE S256, token + revocation endpoints, CIMD fetch (SSRF-safe) **and** a DCR fallback because VS Code starts with DCR and Claude falls back to DCR unless both CIMD values are advertised [F34, F38, F68]. `iss` in authorization responses (RFC 9207) is SHOULD today and "expected to" become MUST (<https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization>, accessed 2026-09-29: "A future revision of this specification is expected to upgrade authorization server inclusion of `iss` from SHOULD to MUST."). Candidate to evaluate rather than hand-roll: Better Auth's MCP, device-authorization and API-key plugins (documented, not tested) [F67, F84, F85].
4. Login for the AS is naturally a **passkey**; the device page and the OAuth authorize page can share one passkey session (analysis).
5. Do not IP-allowlist or IP-rate-limit authenticated traffic: hosted-Claude requests come from one range, `160.79.104.0/21` [F28].
6. Do not rely on `${MOSSHATCH_TOKEN}` expanding in Claude Code until tested; a fixed list of credential-looking names is blanked toward remote servers [F30].

## 4. Expressing "this needs a human passkey" over MCP

| Pattern | How it works | Enforced by | Works when... | Fails when... | Verdict |
|---|---|---|---|---|---|
| **P1 Server-side pending approval** | Tool returns a normal result `{status:"pending_approval", approval_id, approval_url, expires_at, summary}`; nothing executes. Human opens `approval_url`, signs in, taps passkey (UV required); server executes exactly the approved payload; agent polls `approvals_get` or re-calls the tool with the same idempotency key. | **MossHatch server + WebAuthn** | Any client, any protocol era, static or OAuth tokens (analysis) | Human never approves (expires) | **Baseline; the only real control** |
| P2 URL-mode elicitation as UX sugar | Same tool also returns `input_required` with an `elicitation/create` `mode:"url"` pointing at `approval_url` [F16] | Client consent to open the URL only; `accept` != approved [F16] | Modern-era clients that declare `elicitation.url` (Claude Code v2 does) [F32] | Legacy stateless: tested -> isError "cannot receive server-to-client requests"; no capability: tested -> HTTP 400 `-32021` [F24] | Optional accelerator only |
| P3 Form elicitation "Confirm?" | `input_required` with a boolean form | The client UI | modern clients | Auto-answerable by hook [F32]; no passkey; spoofable text; unusable for legacy [F24] | Do not use for money/secrets |
| P4 Tasks extension | Return a task in `input_required` [F17] | Client + server | future clients | Support unverified [F17] | Later |
| P5 Client-side friction: `destructiveHint`, `_meta["anthropic/requiresUserInteraction"]` | Makes some clients prompt every call [F33, F36] | The client | Claude Code >= v2.1.199 [F33] | Other clients ignore; a user can turn prompts off ("Always Allow") [F43] | Complement, not control |
| P6 HTTP 403 `insufficient_scope` | Token lacks the scope; OAuth clients step up [F12] | Server | OAuth clients | Static-token clients just fail | Use for missing scopes, not approvals |

**Recommended contract for money-moving tools (analysis):** the tool is safe to call (it only creates a pending approval), is idempotent on `(token, action-hash)` so an injected agent cannot spam duplicates, returns `isError: false`, and carries only server-generated summary text. The approval page renders the price and terms from the server-side quote, not from agent text. The WebAuthn challenge is a server-stored random value of >=16 bytes [F66], bound in the database to `(approval_id, user_id, action-hash, quote_id, expiry)`; WebAuthn offers no transaction-display feature, so the page itself must show the details [F66]. RFC 9396 `authorization_details` (`payment_initiation` example) is the standards-shaped way to describe such a grant if it is ever exposed over OAuth [F65]. Cap pending approvals per token and per user to blunt approval fatigue [F43].

## 5. Tool catalogue and annotation policy

Annotations are hints; hosted clients use them to decide prompting [F15, F36, F38]. Policy (analysis): **`readOnlyHint: true` only when the tool returns no secret values, costs nothing and changes nothing.** For tools that reveal secrets, set `readOnlyHint: false` and leave `destructiveHint` at its spec default (true) so clients that key on it prompt [F15, F36]. Add `_meta["anthropic/requiresUserInteraction"]: true` on money/reveal tools [F33]. Provide a `title` on every tool (directory rule) [F36]. Tool descriptions must be static text that describes behaviour and never tells the model how to behave [F36, F44].

## 6. Prompt-injection and secret-handling risks (MCP servers touching secrets and money)

Sources: spec security text [F13, F15, F16, F6], OWASP LLM01 [F40], OWASP MCP Top 10 (beta) [F41], Willison's lethal trifecta [F42], Invariant's GitHub MCP disclosure [F43], Microsoft's tool-poisoning guidance [F44]. OWASP is explicit that no fool-proof prevention exists [F40], so the design goal is **limiting blast radius**.

| # | Risk | MossHatch-specific example | Mitigation (analysis unless cited) |
|---|---|---|---|
| R1 | Indirect injection via data we return [F41 MCP06, F44] | Registry/WHOIS text in search results, DNS record contents, secret names/notes typed by a teammate, creature names | Treat all such strings as untrusted data: length caps, control-char stripping, return as structured fields, no free-form "notes" in tool results, never echo instructions |
| R2 | Tool poisoning of our own server [F44, F36] | User-controlled text leaking into tool descriptions/schemas | Static descriptions compiled from code; no per-tenant text in `tools/list`; pin SDK; never auto-load third-party tool descriptions |
| R3 | Lethal trifecta [F42] | Agent with `secrets:reveal` (private data) reads untrusted repo/web content and has `dns:write` (TXT/CNAME to attacker host = exfil channel) or any outbound tool | Token-creation lint: refuse or warn on `secrets:reveal` + `dns:write` together; default env allowlist `["dev"]`; no reveal in default agent tokens; DNS writes to new external targets need passkey |
| R4 | Over-broad scope / scope creep [F41, F83] | One omnibus token for all domains and envs | Fine-grained constraints (domain + env allowlists), short expiry, per-agent identity, no shared service tokens; step-up via passkey for elevation |
| R5 | Confused deputy / token passthrough [F9] | MCP server forwarding a client token or exposing the wholesale registrar API key | MossHatch tokens are audience-bound to MossHatch only; registrar credentials live server-side and are unreachable from any token |
| R6 | Approval fatigue and "Always Allow" [F43] | Injected agent floods purchase requests | Idempotent proposals, caps on pending approvals, approval page shows requesting token name, IP, client info, server-computed price; approvals single-use with 15 min TTL |
| R7 | Secrets in model context and logs [F41, F89] | `secrets_reveal` output lands in the transcript; verbose logs record tool args | Reveal off by default; never log args/results for secret tools; `Cache-Control: no-store`; `cacheScope: private` [F14]; redact before telemetry |
| R8 | Secrets through elicitation [F16] | Asking the user for an API key via a form prompt | Forbidden by spec; use a first-party URL page (secret entry) and verify the person opening it [F16] |
| R9 | `requestState` tampering/replay [F6] | Client edits echoed state to skip a step | Prefer DB-backed approval state; if `requestState` is used keep only `approval_id`, sign with HMAC (the SDK provides a codec that is "signed, not encrypted"), bind principal + TTL, enforce single use in the DB [F6, F24] |
| R10 | SSRF and localhost impersonation in Phase 1 OAuth [F68] | CIMD fetch of attacker URL; malicious local app claiming to be Claude Code | SSRF-safe fetcher (no redirects, block special-use ranges), exact redirect-URI match, show redirect host on consent [F68] |
| R11 | Device-code phishing [F49, F45-F47] | Attacker sends victim a code to type on our /device page | See Section 7.1 |
| R12 | Output too large / cache poisoning [F14, F70] | `secrets_list` of thousands of keys | Pagination; small pages; private cache scope |

## 7. CLI: `mosshatch login`, token storage and `mosshatch run`

### 7.1 Login = RFC 8628 device authorization grant

| Element | RFC 8628 requirement / behaviour [F45, F46, F47] | Recommended MossHatch value (analysis unless cited) |
|---|---|---|
| Device request | `POST device_authorization` with `client_id` (+ `scope`); client SHOULD only start when the user asks | Public client `mosshatch-cli`; start only on `mosshatch login`; scope defaults to CLI-safe set |
| Response | `device_code`, `user_code`, `verification_uri` required; `verification_uri_complete` optional; `expires_in` required; `interval` optional (default 5) | `expires_in` 600 (RFC example is 1800, shorter limits phishing value [F47]); `interval` 5 |
| `user_code` | Rate-limit attempts; 8-char base-20 ~34.5 bits needs about 5 attempts per code for 2^-32 odds [F47] | `XXXX-XXXX` from `BCDFGHJKLMNPQRSTVWXZ`; invalidate the code after 5 wrong entries; also per-IP and per-account limits |
| `device_code` | "a very high entropy code SHOULD be used" (RFC 8628 s5.2, same URL as [F47]) | 256-bit random, stored hashed |
| Display | Client MUST show `user_code` even when using the complete URI; QR/URL open allowed [F45] | Print URL + code, try to open the browser, `--no-browser` flag |
| Polling | `authorization_pending` keep polling at `interval`; `slow_down` -> +5 s permanently; `access_denied`/`expired_token` stop; any other error MUST stop; back off on timeouts [F46] | Implement exactly; server enforces `slow_down` |
| Approval page | RFC: tell the user they authorize a device in their possession and show information about the device [F47] | Passkey with user verification; show CLI name/version, client-declared hostname (marked untrusted), IP, coarse location, time, scopes; require typing/confirming the code; explicit Deny |
| Kill switch | Microsoft recommends blocking device code flow where possible [F49] | Per-account setting to disable device login; audit every grant |
| Issued tokens | - | Access token ~60 min + rotating refresh token [F93]; refresh idle expiry 30 days (Vercel's CLI token idles out at 10 days [F77]) |

### 7.2 Where the CLI keeps credentials

- Keep the **access token in memory only**; store the **refresh token** in the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service) (analysis).
- Library: `@napi-rs/keyring` 2.1.0 (2026-09-13) [F51]. `keytar` 7.9.0 was last published 2022-02-17 and its archive status could not be verified; `@github/keytar` 7.10.6 (2026-02-06) and `cross-keychain` 1.1.0 exist as alternatives [F51].
- **Trap**: on Linux without a Secret Service, `@napi-rs/keyring` silently uses the kernel keyutils store, which is in-memory and lost on reboot; pin `{ linux: { store: 'secret-service' } }` so it throws instead, then choose the fallback deliberately [F87].
- Fallback when no keychain (headless/CI): prefer `MOSSHATCH_TOKEN` from the environment; if a file is unavoidable use `$XDG_STATE_HOME/mosshatch/credentials.json`, dir 0700, file 0600, and print a warning. GitHub's CLI silently falls back to a plain-text file and needs `--insecure-storage` to force it [F50]; do the fallback **loudly** (analysis).
- Key stored credentials by `issuer` and profile (the MCP spec requires clients to key persisted credentials by issuer [F10]; Infisical stores per-profile [F52]).
- `logout` should revoke server-side (RFC 7009 POST) and then delete locally; keep `--local-only` for offline cases (Infisical does exactly this) [F52, F86].
- Never accept tokens as flags: `mcp-remote` and Vercel's own docs both note that argv values are readable through the process list [F39, F71].

### 7.3 `mosshatch run <domain> --env dev -- <cmd>` semantics (recommended)

1. **Syntax**: `run <domain> [--env NAME] -- <cmd> [args...]`; everything after `--` is passed unchanged, no shell unless `--shell` (Infisical, Doppler, 1Password all use `--`) [F52, F54, F56].
2. **Default env `dev`** (Infisical's default) [F52]. Any other env requires explicit `--env` and an `secrets:inject` grant for that env; prod is approval-gated (analysis).
3. **Environment only.** No `.env`, no temp files, no mount in Phase 0. Doppler's own docs call a named-pipe mount the only secure file-system option, which is why files are excluded [F54]. 1Password says to assume same-user processes can read each other's environment, so document that limitation [F56].
4. **Precedence and denylist**: vault secrets override inherited variables (Infisical) [F52]. Refuse to inject reserved names (`HOME PATH PS1 PS2 PWD EDITOR XAUTHORITY USER TERM TERMINFO SHELL MAIL XDG_* LC_*`) [F52] and code-execution-capable names (`LD_PRELOAD LD_LIBRARY_PATH DYLD_INSERT_LIBRARIES PROMPT_COMMAND NODE_OPTIONS PERL5OPT PYTHONWARNINGS PHPRC`) [F54]; enforce at `secrets:write` time as well as at run time (analysis).
5. **Process**: spawn (no shell), `stdio: inherit`. So the wrapper stays alive and must forward signals; the `exit` event yields either a code or a signal name (never both) [F81]. Node's `child_process` has no process-replacing `exec` (analysis).
6. **Signals**: Doppler defaults `--forward-signals` to **off when stdout is a TTY and on otherwise** (source reading) [F75], presumably because a terminal delivers Ctrl-C to the whole foreground process group (analysis); Infisical forwards every signal (source reading) [F53]. Recommended: forward SIGTERM/SIGHUP/SIGQUIT always, SIGINT only when not a TTY, then wait for the child; never exit first (analysis).
7. **Exit code**: return the child's exit status; if killed by signal N return 128+N; 127 = not found, 126 = not executable [F58]. Do **not** collapse non-zero statuses: Infisical's plain `run -- cmd` path appears to return 1 for any non-zero child exit (source reading, not executed) [F53]. Use a small documented set for MossHatch's own failures that avoids 126/127/128+ (analysis). On Windows Ctrl-C yields a non-zero code (Doppler known issue) [F76].
8. **Output masking**: `op run` masks secret values in stdout/stderr by default with `--no-masking` to disable [F88]. Because an agent's shell tool returns child output to the model, default masking on when stdout is not a TTY (analysis; masking is best-effort against encodings).
9. **No exfil helpers**: no `export`/`env` printer; `secrets get` prints only with explicit `--reveal` on a TTY (analysis).
10. **Audit**: server records token id, domain, env, key names injected, IP; never values (analysis, OWASP MCP08/MCP01 [F41, F89]).

## 8. Tokens

### 8.1 Format

- Pattern (analysis, following GitHub's design [F60] and Doppler's per-kind prefixes [F55]): `mh_<kind>_<random32><crc6>` where `<random32>` = 32 chars of base62 from a CSPRNG (32 x log2(62) = 190.5 bits, arithmetic) and `<crc6>` = CRC-32 of the prefix+random, base62, left-padded to 6 chars. The underscore separator is not a base64 character, so random strings such as SHA hashes cannot accidentally match the format [F60].
- Kinds: `pat` (user-created scoped agent/API token), `at` (OAuth/CLI access token), `rt` (rotating refresh token). Optionally `test` vs `live` segment only if a sandbox mode exists (Stripe uses `sk_test_`/`sk_live_`) [F62].
- Detection regex to register: `\bmh_(?:pat|at|rt)_[0-9A-Za-z]{38}\b` (analysis). The checksum lets scanners and MossHatch reject fakes offline [F60].
- Show a token once at creation (Stripe and Doppler do) [F82, F62]; store only a display hint (kind + last 4).

### 8.2 Storage: is SHA-256 enough?

- For **passwords**, OWASP says fast hashes such as SHA-256 are unsuitable because passwords have low entropy [F64].
- For **random secrets**, NIST SP 800-63B-4 requires look-up secrets to be stored hashed with an approved hash, and demands salted slow password hashing only for secrets below 112 bits [F63]. By inference (not stated) a plain SHA-256 is acceptable for a >=128-bit random token (analysis).
- Recommended: store `sha256(full_token)` (bytea, unique index) and look up by that hash. Paragon describes the early-exit timing leak of querying by a raw token and the split-token fix [F72]; looking up by the hash of the whole token gives the same protection because an attacker cannot choose a preimage for a chosen hash (analysis).
- Optional hardening: HMAC-SHA-256 with a KMS-derived pepper so a DB-only leak is inert (analysis; adds a KMS dependency to the auth path).
- GitHub's partner false-positive feedback format accepts SHA-256 token hashes only, another reason to use SHA-256 [F59].
- Never log Authorization headers; hash before any caching (OWASP MCP01 [F41, F89]).

### 8.3 Scoping model

- Scopes are flat `resource:action` strings (the SDK requires names to follow the OAuth scope-token grammar) [F23]. No implicit hierarchy, so the spec's "scope hierarchy" clause is trivially met (analysis).
- **Constraints attached to the token**, not encoded in scopes: `domains` allowlist (exact or glob), `envs` allowlist (default `["dev"]`), `expires_at`, `max_pending_approvals`, optional label identifying the agent. This mirrors OWASP's fine-grained-scope advice and Invariant's "one repo per session" mitigation [F83, F43]. Stripe's restricted keys, including its agent tag, are the closest commercial precedent [F62].
- Escalation rules (analysis): agent tokens can never mint tokens, decide approvals, change billing or manage passkeys; those need a browser session with a fresh passkey assertion. A token's scopes can only be narrowed after creation.
- Resource binding: OAuth access tokens carry `aud` = canonical MCP/API URL and are rejected elsewhere [F9].

### 8.4 Expiry and revocation

| Token | Default TTL | Max | Idle expiry | Notes (analysis unless cited) |
|---|---|---|---|---|
| `mh_pat_` | 30 days | 90 days | 30 days unused | Vercel expires idle CLI tokens after 10 days [F77] |
| `mh_at_` | 60 minutes | 60 minutes | - | Short-lived access tokens SHOULD be used [F93] |
| `mh_rt_` | 30 days | 90 days absolute | 30 days | Rotate on every use [F93]; reuse of an old refresh token revokes the family (analysis) |
| device `user_code`/`device_code` | 600 s | 600 s | - | [F47] |
| approval | 15 minutes | 15 minutes | - | single use |

Revocation must be immediate: opaque tokens looked up in Postgres on every request (no long-lived JWT caches). Provide RFC 7009 revoke [F86], a dashboard kill switch, and automatic revocation when GitHub reports a leak [F59].

### 8.5 GitHub secret scanning

- **Partner program** (the only mechanism that finds leaks in other people's repos): email secret-scanning@github.com, accept GitHub's terms, supply regexes, a test account and an HTTPS endpoint; GitHub POSTs `[{token,type,url,source}]` signed with ECDSA-NIST-P256V1-SHA256 (keys at `api.github.com/meta/public_keys/secret_scanning`) for matches in public repos and public npm packages; treat every reported token as compromised, revoke and notify [F59].
- **Custom patterns** only protect repos in your own org/enterprise and need GitHub Secret Protection for private org repos [F61]; they help scan MossHatch's own repos, not customers'.
- Prep before contacting GitHub (analysis): finalize the format and regex (Section 8.1), stand up `POST /hooks/github-secret-scanning` (raw-body signature verification, key cache, idempotent revoke, email via Resend), keep a test account issuing sample tokens.
- Lead time and eligibility for a pre-launch startup are **unverified**.

## 10. Phasing recommendation (analysis)

- **Phase 0**: REST + `/mcp` behind scoped `mh_pat_` tokens; device-flow CLI login and `run`; approvals with passkey; PRM + AS metadata already published; GitHub partner outreach started; rate limits and audit log.
- **Phase 1**: OAuth authorization-code + PKCE with CIMD and DCR fallback for claude.ai/Desktop connectors and OAuth in Cursor/VS Code; evaluate Better Auth vs custom [F67]; test each client's era support.
- **Phase 2**: URL-mode elicitation sugar for modern clients, Tasks extension when clients support it, `--mount`-style file injection if demanded.

## 11. Design implications

1. Target MCP 2026-07-28 with the v2 TypeScript SDK (@modelcontextprotocol/server 2.2.0, pinned exactly); do not build on @modelcontextprotocol/sdk 1.31.0, which tops out at protocol 2025-11-25. Keep the default legacy:'stateless' posture so 2025-era clients still work. [F19-F21, F24, F73]
2. Host /mcp as one POST-only stateless Vercel /api function (export default { fetch }) that runs, in order: Origin/Host validation, bearer verification (hash lookup) -> AuthInfo with expiresAt, rate limit by token id, then handler.fetch(request, { authInfo }). The SDK handler itself validates none of these (tested). GET/DELETE return 405. [F3, F4, F21-F23, F25]
3. Phase 0 authentication = scoped static bearer tokens (mh_pat_...) that work with Claude Code (--header / .mcp.json headers), Cursor (headers), VS Code (headers with ${input:}) and stdio-only clients via mcp-remote; hosted claude.ai/Desktop connectors need OAuth (static headers are beta for limited orgs), so plan an OAuth AS with CIMD plus a DCR fallback in Phase 1. Publish RFC 9728 and RFC 8414 metadata from day one. [F29, F34, F35, F37-F39, F74, F10]
4. Enforce 'a human passkey must approve anything that costs money' on the server: money tools only create a pending approval (idempotent on token + action hash, isError false, server-generated summary); the human approves on a first-party page with a passkey (UV required, server-stored challenge >=16 bytes bound to the approval); the agent polls approvals_get. Never rely on MCP elicitation for this: clients can auto-answer it (Claude Code Elicitation hook), legacy stateless clients cannot receive it, and clients without the capability get -32021 (both tested). [F16, F24, F32, F66]
5. Treat tool annotations as client-UX hints, not controls: readOnlyHint:true only for tools that return no secret values and cost nothing (VS Code and Claude skip confirmation for them); leave secrets_reveal non-read-only, keep destructiveHint at its default, and add _meta['anthropic/requiresUserInteraction'] on money/reveal tools (honoured by Claude Code >= v2.1.199). [F15, F33, F36, F38]
6. Keep secrets out of model context by default: no secret values in list/describe tools; secrets_reveal is opt-in per token and dev-env-only unless passkey-approved; bulk injection (secrets:inject) is CLI/REST only, never an MCP tool; secret-bearing responses are Cache-Control: no-store and cacheScope private; never log args/results of secret tools. [F14, F41, F89]
7. Neutralize the lethal trifecta for MossHatch: warn or refuse when one token holds secrets:reveal together with dns:write (DNS records are an exfiltration channel); default env allowlist ['dev']; per-domain allowlists; no omnibus tokens; narrow-only scope edits after creation. [F41-F43]
8. Treat every string MossHatch returns that a third party or teammate can influence (registry/WHOIS text, DNS record values, secret names/notes, creature names) as untrusted: caps, control-character stripping, structured fields only, static tool descriptions, no instructions in results. [F36, F41, F44]
9. Never take secrets through form-mode elicitation and never issue pre-authenticated approval URLs; secret entry and approvals happen on a first-party page that verifies the person who opened the URL (session + passkey). Keep any requestState minimal (approval_id), HMAC-signed, TTL- and principal-bound, with single use enforced in Postgres. [F6, F16]
10. CLI login is the RFC 8628 device grant: user_code 8 chars from BCDFGHJKLMNPQRSTVWXZ, <=5 wrong tries per code, expires_in ~600 s, interval 5 with slow_down +5, always print the code even with verification_uri_complete, and an approval page that shows device/IP/location/time/scopes and requires a passkey; offer an account setting to disable device login because device-code phishing (Storm-2372) is real. [F45-F50]
11. Store the CLI refresh token in the OS keychain with @napi-rs/keyring (pin Linux store to secret-service so it throws instead of silently using non-persistent keyutils); avoid keytar (last release 2022-02-17); if there is no keychain prefer MOSSHATCH_TOKEN, else a 0600 file with a loud warning; key credentials by issuer+profile; logout revokes server-side (RFC 7009) then deletes locally. [F50, F51, F52, F86, F87]
12. mosshatch run <domain> --env dev -- <cmd>: env-only injection (no files), default env dev, secrets override inherited vars, refuse reserved names (HOME, PATH, XDG_*, LC_*...) and code-execution names (LD_PRELOAD, NODE_OPTIONS, DYLD_*, PROMPT_COMMAND...) at write time and run time, spawn without a shell with inherited stdio, forward SIGTERM/SIGHUP always and SIGINT only without a TTY, propagate the child's exit code (128+n on signal, 126/127 per POSIX), mask secret values in output when stdout is not a TTY. [F52-F54, F56, F58, F75, F81, F88]
13. Never accept tokens as CLI flags (argv is readable through the process list); take them from env, stdin or the keychain. [F39, F71]
14. Token format mh_<kind>_<32 base62><6-char CRC32 base62> (kinds pat, at, rt): 190.5 bits, offline-checkable, one register-able regex; show once; store only sha256(full token) plus a last-4 hint; look up by hash. SHA-256 is adequate for >=128-bit random tokens (NIST 63B-4 inference); OWASP's slow-hash advice targets passwords. [F55, F60, F62-F64, F72]
15. Enroll in the GitHub secret-scanning partner program early (email secret-scanning@github.com): signed webhook (ECDSA-NIST-P256V1-SHA256 over the raw body), auto-revoke and notify on every report; custom patterns only cover MossHatch's own repos. [F59, F61]
16. Model token power as flat scopes plus separate constraints: scopes mcp, account:read, domains:read, domains:quote, domains:purchase, dns:read, dns:write, secrets:list, secrets:write, secrets:delete, secrets:reveal, secrets:inject, approvals:read, approvals:cancel, audit:read; constraints domains, envs, expires_at, max_pending_approvals, label. Token management, approval decisions, billing and passkey management are never grantable to bearer tokens. [F43, F62, F83, F89]
17. Expiry/revocation defaults to start from: mh_pat_ 30 d (max 90) with 30 d idle expiry, mh_at_ 60 min, mh_rt_ rotating with reuse detection, approvals 15 min single-use, device codes 600 s; revocation is immediate via DB lookup on every request; leak reports revoke automatically. Vercel's 10-day CLI idle expiry is the precedent. [F47, F59, F77, F93]
18. Rate-limit by token id, not IP: Vercel WAF header keys are Enterprise-only, counters are per region, and all Claude-hosted traffic comes from 160.79.104.0/21 (IP limits would throttle unrelated users; do not IP-allowlist tokens). Use @vercel/firewall with a custom rateLimitKey or Postgres counters for money-related caps; emit Retry-After. [F27, F28, F79]
19. Avoid Vercel's April 2026 failure mode (a tier of variables that decrypt to plaintext for anyone with internal access): no weaker tier, every secret (dev included) is KMS-envelope-encrypted with audited, rate-limited decrypt paths and alerts on bulk decrypts, so a compromised employee or third-party session cannot silently enumerate values (analysis). [F57, F78]
20. Paginate list-style tools (Claude Code warns at 10k tokens and caps at 25k) and vary tools/list by the token's scopes so the model only sees tools it can call. [F13, F70]
21. Approval-fatigue controls: cap pending approvals per token (3) and user (10), show requesting token name/IP/client info on the approval page, bind the approval to a server-computed quote, and treat client-declared clientInfo as a log field only. [F2, F43]
22. Design the AS for the hosted-Claude quirks now: real 401 with resource_metadata, PRM resource equal to the MCP URL, primary issuer first, form-encoded token endpoint, S256 PKCE, discovery endpoints answering within 10 s, redirect https://claude.ai/api/mcp/auth_callback plus port-agnostic loopback for Claude Code. [F34]
