# Vercel platform facts for the Mosshatch backend and frontend

Research date and access date for every source below: **2026-09-29**. Analyst: Phase 0 research (live-verified).
Scope: Vercel Hobby/Pro/Enterprise, Functions, Cron, durable async work, security features, domains/TLS, SPA hosting, regions, reliability.

## TL;DR

1. A paid product needs **Pro** ($20/month platform fee, includes 1 deploying seat and $20 usage credit; extra deploying seats $20/month). Hobby is contractually "personal or non-commercial" and its definition of commercial includes "requesting or processing payment from visitors".
2. Use **Node.js Fluid Functions** (Node 24.x default, 22.x ok; Node 20 is disabled for new deployments on 2026-10-01), not Edge (Vercel: "We recommend migrating from edge to Node.js"). Limits: 300s default and 800s GA max duration on Pro (1800s beta), 2 GB/1 vCPU default (4 GB/2 vCPU max), 4.5 MB request/response body, default region iad1 (Neon `aws-us-east-1` is the co-located pair).
3. **Cron on Pro can run every minute** (100 jobs/project, UTC, production deployments only, `Authorization: Bearer $CRON_SECRET`), but Vercel says delivery is "best effort", can be duplicated or silently missed, and failed runs are not retried. A durable Postgres `jobs` table with `FOR UPDATE SKIP LOCKED` claims plus a 1-minute cron sweeper matches Vercel's own guidance and is still the simplest reliable option.
4. **Vercel Queues is Beta** (`@vercel/queue` 0.7.0), **Workflow SDK** is v4 "latest" with v5 pre-release (no GA announcement found), Cron is GA since 2023-11. Do not put the money path on Queues/Workflow yet. Inngest ($0/$99 mo), QStash ($1 per 100K messages) and Trigger.dev ($0/$10/$50 mo) are the credible external options if sub-minute latency is later needed.
5. Security levers are real but shallow: WAF custom rules 40 and rate-limit rules 40 on Pro (counters are **per region**), Attack Mode blocks non-browser clients (would block AI agents), Sensitive env vars are prod/preview only, OIDC (issuer `oidc.vercel.com/<team>`, `sub` = `owner:<team>:project:<proj>:environment:<env>`) federates to AWS/GCP without static keys, runtime logs are only 1 day on Pro.
6. Reliability: 133 status incidents in the last 12 months (3 critical, 28 major, 81 minor); iad1 had a multi-service outage on 2025-10-20/21 (cron jobs affected) and 2026-05-08 (Functions, Queues, Workflow). Pro has no SLA (Enterprise SLA is 99.99%).
7. Wildcard TLS (Let's Encrypt DNS-01) needs Vercel nameservers or an `_acme-challenge` NS delegation to Vercel; two domains (mosshatch.com, hatchkind.com) can live in one Pro project (unlimited domains).
8. If the chosen upstream registrar needs an IP allow-list, Vercel **Static IPs cost $100/month per project** (Pro) and disable the extended-duration and large-function betas.

**Cost of a 1-minute sweeper (my arithmetic, assumptions stated):** 60 x 24 x 30 = 43,200 invocations/month x $0.60/1M = $0.026; at 50 ms Active CPU each = 0.6 CPU-hr x $0.128 = $0.077; at 2 GB held ~1 s each = 24 GB-hr x $0.0106 = $0.254. Total about **$0.36/month**, well inside the $20 credit.

**Implications for a durable `jobs` table + cron polling at 1-minute cadence:**
- Feasible on Pro (Hobby cannot: daily only). Per-minute precision means worst-case pickup latency is about 60 s plus queue depth; use `waitUntil` (section 4) for an immediate best-effort kick and treat cron as the sweeper.
- Vercel's own contract (idempotent, reconciliation-based, locks for overlap) is exactly what a `SELECT ... FOR UPDATE SKIP LOCKED` lease queue gives you.
- Skips leave **no log**, so absence of evidence is invisible: add a heartbeat row (`last_sweep_at`) and an external dead-man alarm; add a second trigger (for example a scheduled GitHub Action or QStash schedule hitting the same protected endpoint) because the claim step makes multi-trigger safe.
- Do not put the cron path behind a redirect or Vercel Authentication challenge; verify `CRON_SECRET` with a constant-time compare and mark it Sensitive.

| **Trigger.dev** | Commercial, v4, `@trigger.dev/sdk` 4.6.4 | Free $0 (+$5 credits, 20 concurrent runs, 1-day logs); Hobby $10/mo; Pro $50/mo | Pricing page has a per-machine compute table, which indicates tasks run on Trigger's own compute rather than your Vercel function (inference), so no 800 s ceiling; adds another vendor holding job payloads. | https://trigger.dev/pricing |

**Verdict (partly inference):** for a money-moving product whose truth already lives in Postgres, the simplest reliable design remains **a `jobs` table written in the same transaction as the business row (transactional outbox), claimed with `UPDATE ... WHERE id IN (SELECT id FROM jobs WHERE run_at <= now() AND status='queued' ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT n) RETURNING *`**, a lease/visibility column (`locked_until`), attempt counter with backoff, and a unique idempotency key per external side effect (registrar order id, Stripe event id). Reasons: (a) exactly the guarantee Vercel's cron docs ask for; (b) atomic with domain state, which Queues/Workflow/Inngest cannot be; (c) Queues is Beta and Workflow's stable status is unclear, both bound to iad1 (incidents 2026-03-06, 2026-05-08, 2026-05-09, 2026-06-25, 2026-07-01); (d) no new vendor sees registrant PII. Neon note: a single-statement claim is a one-shot query and works over the Neon HTTP driver, whereas interactive multi-statement transactions need WebSockets/`pg` (https://neon.com/docs/serverless/serverless-driver: "If you require session or interactive transaction support ... use WebSockets."). The single-statement claim being safe over HTTP is my inference from PostgreSQL semantics.
Revisit Queues/Workflow when Vercel labels them GA, or add Inngest/QStash only if sub-minute latency, fan-out or long human-approval waits become product requirements.

**Queue cost sketch (approximate, inference):** Queues push delivery bills roughly send + notify + receive + delete = about 4 ops per message: 1M messages is about 4M ops = about $2.40 at $0.60/1M. Exact op count per push message is unverified.

## 11. Design implications for Mosshatch

1. **Plan and cost:** one Vercel team on Pro from launch. Baseline $20/month; add $20/seat per extra deployer (viewer seats free). Expected extras: Observability Plus (30-day runtime logs; $1.20/1M events) and Drains ($0.50/GB) are usage-based; Static IPs $100/month only if the registrar demands an IP allow-list (the registrar dossiers `research/reg-opensrs.md`, `reg-namecheap.md` and `reg-dynadot.md` report IP allow-lists; Vercel Static IPs add $100/month/project and disable the 30-minute-duration and large-function betas).
2. **Runtime:** Node.js 24.x Fluid Functions in `/api`, `export default { fetch }` Web handlers (raw `Request` body for Stripe/Resend/registrar webhook signature checks), `engines.node: "24.x"`, no Edge runtime. Keep bodies < 4.5 MB, set `maxDuration` explicitly (for example 60 s for API, 300 s for the sweeper), and keep pool size small (1,024 shared file descriptors) with `attachDatabasePool`. Because Fluid shares one instance across concurrent requests, never keep per-request auth or tenant state in module globals.
3. **Region:** pin `"regions": ["iad1"]` in vercel.json (do not rely on the default) and create the Neon project in `aws-us-east-1`; put the cloud KMS in `us-east-1` if AWS. Accept iad1 as a known single point of failure (2025-10-20, 2026-05-08). Write a runbook for a region switch (change `regions`, redeploy, point at a Neon replica/branch) and note Node cross-region failover is Enterprise-only. Do not rely on Pro "multi-region" without also solving the database.
4. **Async jobs:** Postgres `jobs` table + `SKIP LOCKED` claim + lease + idempotency keys; Vercel Cron `* * * * *` sweeper on `/api/cron/jobs` with `Bearer CRON_SECRET`; `waitUntil` for the fast path; a heartbeat table and external dead-man's switch because skipped crons leave no log; optionally a second trigger (GitHub Actions schedule or QStash) hitting the same endpoint. Money side effects (registrar order, Stripe refund) run only from claimed jobs with unique idempotency keys so duplicate cron deliveries are harmless. Do not adopt Queues/Workflow for the money path until GA.
5. **Approval of spend:** do not depend on Vercel WAF rate limits (per-region counters, IP/JA4 keys only on Pro) for velocity limits on money-spending actions; enforce velocity, per-token budgets and passkey-approval requirements in Postgres, and use WAF/`checkRateLimit` as an outer layer keyed by token id. Do not turn on Attack Mode permanently (it "could" block AI agents and CLI clients); use targeted custom rules and BotID Basic only on human browser routes (login, checkout, passkey ceremony), never on agent API routes.
6. **Secrets:** Production env vars as Sensitive; enable the team policy "Enforce Sensitive Environment Variables"; `CRON_SECRET`, Stripe, Resend and registrar keys all Sensitive. Non-sensitive env vars are readable by every project member. Keep vault key material out of Vercel entirely: use OIDC to assume an AWS role (or GCP WIF) with a trust policy pinned to `sub = owner:<team>:project:<project>:environment:production`, team issuer mode, custom audience, and a separate role/key for preview. Set `AWS_REGION` explicitly. Vercel KMS (Beta) only signs; it does not replace the vault KMS.
7. **Headers:** ship CSP, `Permissions-Policy` (deny camera/mic/geolocation; allow `publickey-credentials-get`/`create` for self), `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, and explicit HSTS via vercel.json `headers` on `/(.*)`; long-immutable cache on `/assets/(.*)`; `no-cache` on `index.html`. Three.js needs `worker-src`/`blob:` decisions in the CSP dossier (`tech-fonts-csp-headers.md`).
8. **Previews:** Standard Protection (previews behind Vercel Authentication, production public). Crons and Stripe webhooks do not run on previews; use the bypass query parameter for webhook tests. Preview hostnames cannot be the production passkey RP ID (see WebAuthn dossier).
9. **Domains:** attach mosshatch.com and hatchkind.com to one Pro project; choose one canonical host and redirect the other (do not put a redirect in front of the cron path). Use wildcard only if creature subdomains (`*.hatchkind.com`) are a product feature: that requires Vercel DNS or the `_acme-challenge` delegation, and a wildcard does not cover the apex. Keep customer-owned registrations at the upstream registrar, not at Vercel Domains.
10. **Observability and audit:** configure a Log Drain on day one (Pro) to durable storage because Pro keeps runtime logs for 1 day; never log secrets or full registrant PII (1 MB/request cap; drains bill per GB). Vercel Audit Logs/Audit Log Drains are Enterprise-only, so keep the product's own audit trail in Postgres.
11. **Spend safety:** keep the default $200 budget notification, add a webhook alert, and do **not** enable "Pause Production Deployments" without a tested runbook: for a registrar, pausing production mid-order is worse than overspending.
12. **Continuity:** 46 of 133 incidents touched Builds/Deploy; assume you may be unable to deploy during an incident, so ship risky changes behind feature flags stored in Postgres and rely on Instant Rollback (note it does not update crons).
13. **Revisit list:** Queues/Workflow GA, Vercel KMS GA and encrypt/decrypt support, Pro multi-region count, Node failover on Pro.
