# Verification notes: reg-centralnic, lens TECH (technical / pricing)

Verifier run 2026-09-29. Every source below was fetched by me on 2026-09-29 (curl -sSL with browser UA via the agent proxy; headless Chromium for the JS-rendered pricing grid). I did not reuse the analyst's cached copies. Evidence lives in `research/vt-cn/` (raw/ = downloads, kb/ = KB pages as text, pricing-parsed.json, pricing-rendered.txt, status.atom). No account exists, so nothing was tested with credentials; the only live calls were two unauthenticated GETs to the REST hosts.

Overall: the analyst's API-coverage table and the rate-limit, DNS, sandbox and price findings hold up against primary sources. Corrections: (1) default renewal mode, (2) what StatusDomain `status[]` actually is, (3) "identical" OT&E vs production specs, (4) OT&E password menu path, (5) the 100-domain "contradiction" is inside a single FAQ answer, (6) several nuances. Additional items missed are listed at the end.

### OpenAPI OT&E vs production comparison
- Path set identical (208), 287 operations each. Parameter names and request-body property names are identical in 286 of 287 operations; POST /acmeaccount differs (body property `domain` only in OT&E). Every operation differs in raw JSON (x-ptf-command labels, response schemas, descriptions), so "identical parameters" is right, "identical spec" is not. Info.version: 2.0.0-ote.3 vs 0.0.3.
- Live probes (unauthenticated, no credentials sent): `GET https://rest-ote.rrpproxy.net/v1/account` returned HTTP 401 with body {"code":530,"description":"Authentication failed; No authentication data provided"}; `GET https://rest.rrpproxy.net/v1/account` returned HTTP 400 with {"code":505,"description":"Invalid attribute value syntax; LOGIN: ()"}. Both hosts are live, Swagger UI pages return 200. The two environments therefore do not respond identically even to a missing-credentials request (401 vs 400): treat OT&E success as not fully predictive of production HTTP-status handling. HTTP status mapping is otherwise undocumented (spec lists only 200/default).

## 2. Sandbox / OT&E
- Exists: confirmed. https://kb.centralnicreseller.com/how-to/building-your-integration/testing-in-ote/ : "CentralNic Reseller gives every reseller a dedicated OT&E environment"; REST OT&E base https://rest-ote.rrpproxy.net/v1; HTTPS gateway api-ote.rrpproxy.net with s_opmode=OTE; exact hostnames in Control Panel API > API Gateways. Product page https://www.centralnicreseller.com/rest-api/ : "Create a CentralNic Reseller account to access the REST API, documentation, and OT&E sandbox. Once your account is created, you can generate API credentials".
- Credentials: OT&E login = standard account login, OT&E password set from the live Control Panel ("Authentication fails only in OT&E | No OT&E password has been set"; https://kb.centralnicreseller.com/how-to/building-your-integration/authentication-credentials-ip/). The menu path is given three different ways: auth guide "Account -> Settings -> Passwords", OT&E guide "Account -> Password & Security", FAQ (https://www.centralnicreseller.com/faqs/) "Account -> Security & Passwords". Conflict on prod/OT&E credential equality confirmed: REST guide "OT&E credentials do not work against production"; cutover guide "By default, OT&E credentials are identical to the production ones, but individual changes may apply". Password policy 10-64 (auth guide, twice) vs 8-32 (same page, line ~187): confirmed.
- What it simulates: registration end to end and transfer end to end "including the asynchronous status flow", premium via designated test names; nothing billed; data never carries over. Expiry/redemption/DNS resolution/.ai/.io behaviours: not documented (unverifiable).
- Whether OT&E is usable before EUR 75 funding / verification: unverifiable. FAQ says an activated-but-"unverified" account is limited to the initial EUR 75 balance and "The amount of allowed API commands is limited as well, as you are in the Basic price scale".
- MISSED by analyst: https://kb.centralnicreseller.com/help/newsletters-maintenances-status/ says OT&E has "Regular OT&E Bi-weekly Maintenance ... every two weeks on a Wednesday in even calendar weeks at 09:00 CEST / 07:00 UTC ... limited reachability ... should not exceed 2 hours", not listed on the status page. Plan any soak test around it.

## 3. Rate limits
- Confirmed. EPP FAQ (https://kb.centralnicreseller.com/api/epp-server/frequently-asked-questions/): "Is there a rate limit ...? One (1) command per second." "Does this value apply to one IP ... or account? To the account." "Five (5) connections per registrar", idle 10 min, session TTL 24 h. EPP guide repeats "1 command per second, measured across the whole account, not per connection". Transfer-in guide: "CentralNic Reseller enforces roughly one command per second across the account" for API automation (only non-EPP statement). REST-specific limits: none documented (spec has no 429/Retry-After). 422 "Abuse detected! The account has been temporarily locked! Please standby some minutes." and 421 "Client should try again": confirmed in return-codes page. The official Node SDK (npm @team-internet/apiconnector 11.0.0, which I downloaded and grepped) has no rate-limit or retry logic. The 1 cmd/s figure is documented for EPP only; applicability to REST is inference.

Tiers (FAQ): Basic Plus "less than 250 domains" (tooltip says "less than 249"), Pro Plus 250-999, Elite Plus "over 1,000". - Analyst's quote about the 100-domain rule: the pricing page FAQ answer "Is there a minimum purchase requirement?" says "No, there is no minimum purchase required to access our domain reseller pricelist" and, in the very next paragraph of the same answer, "to qualify as a CentralNic Reseller's customer, you should either register a minimum of 100 domains within one year or transfer at least 100 domains". The FAQ page (https://www.centralnicreseller.com/faqs/) says the same with "You'll also need API access". Not independently confirmable: Verisign fee pages redirected to its home page and my web-search budget was exhausted. Unverifiable.
- Design consequence worth adding: .ai registers/renews only in multi-year steps (registration 2-10 years, renewal 2-9 years, https://kb.centralnicreseller.com/domains/tlds/ai/), so a 1-year quote for .ai cannot exist, and a .ai transfer bills 2 years. .io: registration 1-10, renewal 1-9, 60-day registry lock after registration, transfer needs auth and domain older than 60 days, "Handle updates: no".

## 5. Lifecycle / renewal correction
- https://kb.centralnicreseller.com/domains/renewal-system/ section 3.2: "The default account setting is AutoRenew." Section 6.1: "reseller accounts are by default pre-configured for auto-renew". https://kb.centralnicreseller.com/how-to/start-here/your-first-day/ calls AUTORENEW "the safe default for most resellers". The dossier's "DEFAULT = delete at end of term" is wrong: domain-level `DEFAULT` means "inherit the account setting", and the "automatic deletion" wording belongs to the alternative AutoExpire/AutoDelete strategy. Consequence: out of the box a Mosshatch account auto-renews on the renewal date and debits the prepaid balance without any Mosshatch-side approval; approval-gated renewal requires explicitly setting the account (ModifyRegistrar renewalmode) or each domain to AUTOEXPIRE/AUTODELETE/RENEWONCE. Unfunded AUTORENEW domain -> left to expire and removed; recovery needs a paid restore (line 159).
- Renewal date 35 days after expiry for gTLDs (45 - 8 ERRP - 2 buffer), RGP 30 days then 5 days pending delete: confirmed on the renewal-system page.

## 7. Missed by the analyst (technical)
1. OT&E bi-weekly maintenance (even-week Wednesdays 07:00-09:00 UTC in summer time, up to 2 h).
2. `x-registry-status[]` in StatusDomain plus the fact that `status[]` is not documented as the EPP set; ccTLD EPP status support is limited.
3. Account default renewal mode is AutoRenew (analyst reversed it).
4. Account-level lock policy property GENERAL-DEFAULT-CLIENTTRANSFERPROHIBITED and that the auto-lock only applies where the registry supports it; extra statuses clientRenewProhibited, registrar-lock, registrar-hold are writable.
5. OT&E and production respond differently to an unauthenticated request (401/530 vs 400/505); spec response schemas differ; POST /acmeaccount body differs.
6. Three different menu paths documented for the OT&E password.
7. Transfer status values FOREIGN_PENDING and USERTRANSFER.
8. Sign-up attestation (https://www.centralnicreseller.com/sign-up/) reads in full: "this account will only be used by either a legally established business entity or for the management of domain portfolios held outside the EU and not be used by private individuals based within the EU ... may be terminated with immediate effect". This is wider than the analyst's shortened quote and could be read as restricting EU-consumer end-registrants; it is a legal question, flag for the legal lens.
9. Unverified accounts: "amount of allowed API commands is limited" (analyst had it) - the limit itself is not quantified anywhere.
10. Tier boundary wording inconsistent (Basic Plus "less than 249" tooltip vs "less than 250" FAQ; exactly 1,000 domains falls in no tier).
