# Mosshatch Phase 0: WebGL2 + three.js reality check

Accessed for every source below: **2026-09-29**. Author: research analyst subagent. Scope: procedural, shader-heavy scene, 60 fps target on a mid-range phone, at most ~60 draw calls, no model files or textures, DPR capped at 1.75.

Finding IDs (F1, F2, ...) are stable labels shared with the structured summary; they are not contiguous.

## TL;DR

1. **Keep WebGL2 + `WebGLRenderer` + GLSL `ShaderMaterial` for Phase 0.** WebGL2 is 96.44% of global usage (caniuse-db 2026-09-28); floors are iOS/Safari 15.0 and Chrome for Android 58. three's own manual calls `WebGLRenderer` "the recommended choice for pure WebGL 2 applications" and says custom `ShaderMaterial`/`RawShaderMaterial`/`onBeforeCompile` "are not supported in `WebGPURenderer`" (F11).
2. **WebGPU now ships in every major browser engine, with platform gates, so it is not a safe sole target.** caniuse: 85.72% full + 3.05% partial. Chrome Android needs Android 12+ and specific GPU vendors (Samsung Xclipse "probably 154", others "TBD"); iOS 26+ is only 75% of iOS Safari usage. three's `WebGPURenderer` is still "in an experimental state" (F7-F12). Fallback story exists (automatic WebGL2 backend) but needs a TSL rewrite of the shaders.
3. **three.js is 0.186.1 (2026-09-24); cadence slowed from ~32-day to ~70-day gaps; ESM-only; r187 is pending.** Watch: `Clock` deprecated (use `Timer`), WebGL1 gone since r163, `ColorManagement` on by default, `ShaderMaterial` must include `colorspace_fragment` itself (F15-F28).
4. **Shader portability:** WebGL2 (ESSL 3.00) gives IEEE-fp32 `highp`, core `fwidth`, general loops, `uint` bit ops. Avoid `fract(sin())` hashes (spec: trig precision "undefined"), use `uint` hashes; drive `gl_FragCoord` math from `renderer.getDrawingBufferSize()`, not CSS size (F29-F37). Verified in headless Chromium/SwiftShader (three r186): ES1.00 `RawShaderMaterial` fails on `fwidth`; legacy `#extension GL_OES_standard_derivatives` errors.
5. **"60 fps" is conditional on the platform:** WebKit source halves `requestAnimationFrame` to 30 fps for Low Power Mode, visually-idle and aggressive thermal mitigation, and gives pages/frames flagged `OutsideViewport` one frame per 10 s (a page/frame-level reason, not per-canvas); Apple says Low Power Mode may "Reduce CPU and GPU performance" (F42, F48). Build adaptive resolution + a 30 fps mode; there is no web thermal API on mobile (F41).
6. **Snapshot:** call `toBlob` in the same task as `render()` (tested: same task = correct pixel, later task = transparent black) or render to an sRGB `WebGLRenderTarget` (tested: linear RT reads back 128, sRGB RT 188). iOS per-canvas area cap in current WebKit source is 8192x8192 (F46).
7. **Budgets to defend** (section 10): 16.7 ms frame (33.3 ms fallback); ~1.0-1.25 MP drawing buffer at DPR 1.75 (34% of the pixels of DPR 3); draw calls <=60 (Arm guides <500 on GLES natively, so 8x headroom); overdraw budget 2.5x (Arm); no MSAA, no discard, no blending on full-screen layers; ~130 KB gzip for the three chunk (measured).
8. **Cannot be verified without real devices:** sustained thermal curves, hatching-shader ALU cost on Mali/Adreno/Apple, mediump vs highp visual risk, iOS memory-kill thresholds, active-context limits on phones, Safari canvas-noise behavior on snapshots (section 11).

**Decision (confirmed): WebGL2.** Reasons, all cited: (a) GLSL `ShaderMaterial` is unsupported in `WebGPURenderer` (F11) and the project's look is a custom screen-space hatching shader; (b) Android WebGPU is vendor-gated (F9); (c) 25% of iOS Safari is not on iOS 26 (F10); (d) ~80-85 KB gzip extra JS (F13) and a HalfFloat default output buffer (F12); (e) `WebGLRenderer` is "still maintained" (F11).
**Fallback story:** WebGL2 is the floor. three >= r163 has no WebGL1 path ("`WebGLRenderer` no longer supports WebGL 1", migration guide 162 to 163), so when `getContext('webgl2')` fails (about 3.6% of global usage per F1) or `failIfMajorPerformanceCaveat` trips (software rasterizer), show a non-WebGL fallback (static SVG/CSS creature). Use `three/addons/capabilities/WebGL.js` (`WebGL.isWebGL2Available()`), which the manual documents: https://threejs.org/manual/pages/webgl-compatibility-check.html. **Upgrade path later:** keep shader logic isolated so it can be ported to TSL, then flip to `WebGPURenderer` (auto WebGL2 backend) when the manual drops "experimental"; recheck each release.

### 3.3 Tree-shaking guidance

- **No official tree-shaking guidance exists in the three manual**: I fetched all 60 pages listed in `https://threejs.org/manual/list.json` and none contains "tree-shaking". The Installation page says "Installing from the npm package registry and using a build tool is the recommended approach" and shows `import * as THREE from 'three'` (https://threejs.org/manual/pages/installation.html). The only structural signals are package.json `sideEffects: ["./src/nodes/**/*"]`, named exports, and the r168 note that chaining features were removed "to improve tree-shaking of `WebGPURenderer` and TSL".
- **Measured reality (F13):** tree-shaking barely helps once `WebGLRenderer` is imported because it references all shader chunks and material programs. Minimal scene (WebGLRenderer + Scene + PerspectiveCamera + Mesh + PlaneGeometry + ShaderMaterial + InstancedMesh + Timer + `mergeGeometries`): **134,402 B gzip** (esbuild) / **130,392 B gzip** (Vite 8.3.1). A renderer-less import (math + geometry + material classes only): 71,079 B gzip. `import * as THREE` with a Mesh + MeshBasicMaterial: 132,062 B gzip, versus 132,096 B for the same scene with named imports and a `ShaderMaterial` (e.js). So named vs namespace imports makes no measurable difference; budget ~130 KB gzip for three itself and lazy-load the chunk (do not count on shaving it).
- Use `renderer.compileAsync(scene, camera)` at load: it uses `KHR_parallel_shader_compile` where present (`WebGLRenderer.js` line 1555), avoiding first-frame jank from shader compilation (MDN best practices: "Compile Shaders and Link Programs in parallel" / "Prefer KHR_parallel_shader_compile", https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

### 3.4 Renderer defaults worth knowing (r186 source, `WebGLRenderer.js` constructor)

`depth = true, stencil = false, alpha = false, antialias = false, premultipliedAlpha = true, preserveDrawingBuffer = false, powerPreference = 'default', failIfMajorPerformanceCaveat = false, outputBufferType = UnsignedByteType`. The real context is created with `alpha: true` regardless of the option (`contextAttributes = { alpha: true, depth, stencil, antialias, ... }`), which sidesteps MDN's warning "Avoid alpha:false, which can be expensive". With the default `UnsignedByteType`, `WebGLOutput` (an extra full-screen tone-map/output pass into an intermediate target) is **not** created: `if ( _outputBufferType !== UnsignedByteType ) { output = new WebGLOutput(...) }`. Keep the default; setting `outputBufferType: HalfFloatType` or calling `setEffects()` adds a full-screen pass and a 2x wider buffer (fill-rate cost on the very thing that is fill-rate bound). (F27)

## 10. Performance budget numbers (defensible, with basis)

"Cited" = a vendor/spec statement supports the number; "derived" = arithmetic on cited inputs; "measured" = my run; "judgement" = engineering choice with no direct citation (flagged so nobody mistakes it for a vendor limit).

### 10.1 Pixel counts (why DPR 1.75 matters)

| CSS viewport | DPR 1 | 1.5 | **1.75** | 2 | 2.625 | 3 |
|---|---|---|---|---|---|---|
| 360x800 | 0.29 MP | 0.65 | **0.88** | 1.15 | 1.98 | 2.59 |
| 390x844 | 0.33 MP | 0.74 | **1.01** | 1.32 | 2.27 | 2.96 |
| 412x915 | 0.38 MP | 0.85 | **1.15** | 1.51 | 2.60 | 3.39 |
| 430x932 | 0.40 MP | 0.90 | **1.23** | 1.60 | 2.76 | 3.61 |

DPR 1.75 = **34%** of the pixels of DPR 3 (and 44% of DPR 2.625) for every phone size above. Adaptive scale steps on top of DPR 1.75: 1.0 = 100% pixels, 0.85 = 72%, 0.75 = 56%, 0.7 = 49%, 0.6 = 36%, **0.5 = 25%** (effective DPR 0.88). three manual on why not to use raw DPR: "The current top of the line phones have an HD-DPI ratio of 3x meaning for every one pixel from a non-HD-DPI display those phones have 9 pixels. That means they have to do 9x the rendering." and "This is strongly NOT RECOMMENDED." for `setPixelRatio(window.devicePixelRatio)` on heavy apps (https://threejs.org/manual/pages/responsive.html). Throughput at 390x844 @1.75: 1,007,314 px x 60 = **60.4 Mpx/s**; with Arm's assumed 2.5 average overdraw = **151 Mfrag/s** (Arm formula: available cycles per fragment = 0.8 x cores x clock / fragments per second; the GPU inputs for the target phone are not verified here, so I do not publish a cycles/fragment number).

## 11. Risks that cannot be verified without real devices

1. **Sustained thermal behavior**: no web thermal API on phones (F41, F48e). 60 fps for 30 s on a cool phone says little about minute 10; need 10-15 minute soak tests on at least one mid-range Mali, one Adreno and one iPhone, with the phone in a case, on battery, screen at fixed brightness.
2. **Actual fragment cost of the hatching shader** per GPU family (ALU cycles, register pressure/occupancy, texture-less so bandwidth is low but write bandwidth at 1 MP x 60 fps is not zero). Need vendor offline compilers/profilers (Mali Offline Compiler, Adreno tooling, Xcode GPU Frame Capture on a Metal-backed Safari).
3. **`mediump` vs `highp`** visual corruption vs the up-to-2x Adreno gain (F36): device A/B only.
4. **`fract(sin())` vs `uint` hash** output equivalence across drivers is by spec undefined; the visible difference (pattern flicker/banding) cannot be quantified without devices.
5. **iOS memory ceilings**: total canvas/GPU memory before jetsam kills the tab; the "256 MB total canvas memory" figure is not confirmed in current WebKit source (F46d); behavior with a 2048x2048 snapshot RT plus live canvas on a 3-4 GB iPhone is unknown.
6. **Maximum live WebGL contexts** on Chrome Android / Safari iOS (F47): Chromium's value is a runtime preference I could not locate; manual says "typically ... around 8".
7. **Safari canvas privacy noise** on `toBlob` (F46e): whether a first-party app on iOS 26 with Advanced Fingerprinting Protection / Private Browsing ever gets the solid-color noise image is not established.
8. **Low Power Mode**: WebKit source says 30 fps; shipped iOS 26 behavior, and whether `respondToThermalPressureAggressively` is on by default, unverified. Chrome Android battery-saver frame-rate limits: not researched.
9. **MSAA cost through ANGLE** on Mali/Adreno for WebGL default framebuffers (F40) and whether `EXT_multisampled_render_to_texture` is used by the browser: unverified.
10. **SRGB8_ALPHA8 render targets and `readRenderTargetPixelsAsync`** on iOS/Android GPUs: verified only on SwiftShader; `EXT_color_buffer_float`/half-float paths on older iOS (BCD: `EXT_color_buffer_half_float` Safari 14, `OES_texture_float_linear` "Only supported on iPadOS") need device checks if any float target is used.
11. **`KHR_parallel_shader_compile` and program-link stalls** on low-end Mali/Adreno (first-frame time, shader cache hit rates on second launch): device only.
12. **WebGPURenderer WebGL-backend performance** relative to `WebGLRenderer` on phones, and the effort of porting the GLSL to TSL: not measured.
13. **Crowd-sourced limits** (Web3D Survey) are undated and skew to WebGL-using sites; treat as directional.
14. **Real user mix**: caniuse gives global shares; Mosshatch's audience (developers, likely desktop-heavy plus iPhone) will differ.
15. **OffscreenCanvas worker** latency/jank on iOS 17+ with three r186: not tested (and not recommended for Phase 0).
16. **Accessibility conformance** (WCAG 2.2.2 pause mechanism, 2.3.1 flashing) needs manual/AT testing; the hatching flicker rate is a shader property to be measured on real displays.

## 13. Design implications for the Phase 0 plan

1. **Renderer:** `THREE.WebGLRenderer({ antialias:false, alpha:false (context alpha stays true internally), depth:true only if depth test is needed, stencil:false, powerPreference:'default', failIfMajorPerformanceCaveat:false or true if you want a software-render detector })`, `outputBufferType` default. Do not import `three/webgpu` in Phase 0.
2. **Write shaders as GLSL ES 3.00 via `ShaderMaterial`** (never `RawShaderMaterial` without `glslVersion: THREE.GLSL3`); no `#extension` lines; `uint` hashes; explicit `precision`; end with `#include <colorspace_fragment>`. Keep the shader logic in separate `.glsl` modules so a later TSL port is mechanical.
3. **Drive resolution uniforms from `renderer.getDrawingBufferSize()`**, never CSS size or `innerWidth`; recompute on every resize and adaptive-scale change.
4. **Adaptive resolution controller** (rAF-delta based, 250 ms windows, 0.1 steps, floor 0.5, hysteresis, flip-flop lock) + a 30 fps mode; treat 30 fps as a supported state (WebKit Low Power Mode), not a failure.
5. **Lifecycle hygiene:** one context; `webglcontextlost` -> stop loop; `webglcontextrestored` -> rebuild RTs/uniform state and resume; on unmount call `renderer.dispose()` **and** `renderer.forceContextLoss()`; pause on `visibilitychange`, `IntersectionObserver`, and the user's pause control; `Timer.connect(document)`.
6. **Accessibility:** honor `prefers-reduced-motion` (static or slow-motion creature), provide a visible pause/stop control (WCAG 2.2.2 is Level A), keep any flicker below 3 flashes/s (2.3.1).
7. **Audio:** off by default; create/`resume()` the `AudioContext` inside the click/touchend handler of an explicit control; handle `suspended`/`interrupted`; no autoplay; persist the choice.
8. **Snapshots:** same-task `render()` + `toBlob()` on the live canvas when the aspect/size match; otherwise an sRGB `WebGLRenderTarget` (<=2048x2048, `depthBuffer` off if unused), `readRenderTargetPixelsAsync` -> small 2D canvas -> `toBlob`; free it immediately; detect a uniform-color result (Safari noise) and fall back.
9. **Draw-call plan:** one fullscreen triangle for the background/hatching, `InstancedMesh` per creature part type (per-instance seeds in `InstancedBufferAttribute`), `mergeGeometries` for static bits, avoid `BatchedMesh` unless `WEBGL_multi_draw` is present; assert `renderer.info.render.calls <= 60` in a Playwright/SwiftShader CI test.
10. **Fallback ladder:** WebGL2 OK -> full; WebGL2 present but software rasterizer/caveat -> 30 fps + scale 0.5 or static; no WebGL2 (about 3.6% globally) -> static SVG/CSS creature. No WebGL1 path (three >= r163).
11. **Perf validation plan (pre-launch):** device matrix (>=1 Mali mid-range Android, >=1 Adreno, >=1 iPhone on iOS 26 incl. Low Power Mode on, plus an iPhone on iOS 17/18), 15-minute soak, record frame time histograms (not fps), thermal state via OS tooling, and the hatching shader profiled with the vendor tools named in section 7.
12. **Pin and watch:** pin `three@0.186.1` + `@types/three@0.186.0`; upgrade in steps of <=10 releases (guide advice); re-read the migration guide each bump; at the ~70-day cadence expect r187 imminently (`WebGLRenderer.setViewport` pixel-ratio behavior change matters for RT snapshots).
