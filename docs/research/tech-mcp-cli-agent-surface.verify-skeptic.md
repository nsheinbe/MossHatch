## B. Important facts the analyst missed or under-weighted

1. Stripe agent-tagged restricted keys are "automatically subject to approval rules, which require a designated reviewer to approve sensitive actions before they take effect" with default rules for payouts, refunds and account-configuration changes (docs.stripe.com/keys, "API keys for autonomous agents"). This is the closest commercial precedent for MossHatch's server-enforced human approval on money actions; F62 cites only the tag.
2. Anthropic's "Build an MCP server for Claude" page (claude.com/docs/connectors/building/index.md) says: Claude follows the 2025-03-26, 2025-06-18 and 2025-11-25 authorization specs (no 2026-07-28 mention); Claude does not yet support resource subscriptions, sampling, or "advanced or draft capabilities" (elicitation is not listed as supported); limits are ~150,000 characters per tool result and 240 s per tool call on claude.ai/Desktop, versus 25,000 tokens and MCP_TOOL_TIMEOUT on Claude Code; Streamable HTTP is recommended and HTTP+SSE still works. This partly resolves the analyst's "unverified: claude.ai 2026-07-28 support" (documented as not yet) and reinforces keeping the dual-era `legacy:'stateless'` default and a non-elicitation approval path. Better Auth's reference config uses `legacy: "reject"`, which would not work with hosted Claude today.
3. Claude Code `headersHelper` (code.claude.com/docs/en/mcp lines ~700-720): a command that prints a JSON header map, run on each connect, re-run on 401/403 with one retry, 10 s timeout, Authorization from it disables OAuth fallback. It lets a `mosshatch` CLI hand Claude Code a short-lived `mh_at_` token from the keychain instead of a 30-day static `mh_pat_` in .mcp.json. Not in the dossier.
4. Official MCP extensions for machine callers: `io.modelcontextprotocol/oauth-client-credentials` (JWT bearer assertions per RFC 7523 preferred, client secrets allowed) and `enterprise-managed-authorization` (modelcontextprotocol.io/extensions/auth/...). Client support cells in the matrix are not text-extractable, so support is unknown, but this is the standards-track alternative to bespoke PATs for headless agents. Claude's auth page also lists `oauth_anthropic_creds` and `custom_connection` types (contact mcp-review@anthropic.com) as alternatives when DCR/CIMD are undesirable.
5. mcp-remote 0.14.3 (2026-09-21) now has a `--protocol auto` mode that bridges a 2026-07-28 server for legacy stdio clients (rewrites requests, bridges input_required and subscriptions/listen, 10-round cap); default is `legacy`. Fine while MossHatch serves both eras; needed if it ever sets `legacy:'reject'`.
6. Spec compatibility matrix (basic/versioning): legacy client + modern-only server "Fails ... no fall-forward mechanism"; dual-era server works with both. This is the normative reason for the analyst's dual-era posture and should be cited.
7. Secure Payment Confirmation (w3c.github.io/secure-payment-confirmation, Editor's Draft 2026-07-02) is the WebAuthn-based mechanism where the browser displays payee/amount; still an ED, so the analyst's "WebAuthn has no transaction display, the page must show details" remains the safe assumption, but SPC is the thing to watch.
8. VS Code release notes 1.130-1.139 contain no mention of 2026-07-28, stateless MCP or CIMD; VS Code's MCP doc still describes DCR-then-client-credentials. Corroborates "unverified" and suggests VS Code is still on the 2025 era.
9. Claude Code persists over-limit tool output to disk under ~/.claude/projects/.../tool-results (see row 19); relevant to any secret-returning tool.
10. Vercel docs vocabulary changed (Sensitive -> Secret/Config, Secrets allowed in Development) and Vercel's own token format now carries a prefix (`vcp_` in the CLI docs example), another data point for prefixed tokens.
11. Microsoft updated the Storm-2372 attribution on 2026-07-31 (sub-cluster of Midnight Blizzard).
