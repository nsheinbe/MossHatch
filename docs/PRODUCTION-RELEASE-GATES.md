## Commercial and operational gates

The current source uses a $3 annual fee below $50 wholesale, $9 from $50 to below $100, and $10 at $100 or more; the quote uses the greater of operation and renewal cost before the fee. These are preserved source rules, not verified current account economics.

For the representative one-year `.studio` source row, provider cost is $31.20 and retail is $34.20. Assuming domestic processing at 2.9% + $0.30 and a **scenario-only** provider funding fee of 3%:

`34.20 - 31.20 - (0.029 × 34.20 + 0.30) - (0.03 × 31.20) = $0.7722`, or **$0.77** contribution before overhead.

With an assumed 5.4% + $0.30 processing scenario (including applicable international/conversion additions), the same calculation yields **−$0.0828**, or **−$0.08**. Neither funding nor conversion charges are asserted for this owner's account. These examples exclude membership allocation, infrastructure, support, tax services, disputes, and refund losses; they are not net profit. Processor charges can apply to collected tax, which is a liability rather than margin, and refunded purchases can retain processing costs. The immutable economics report contains the source and fee assumptions.

## Authorization required for any future provider exercise

No real-provider exercise is authorized by this document. Before starting one, obtain a written, bounded authorization containing all of the following:

1. **Identity and scope:** the exact provider, sandbox environment and endpoint, isolated test tenant, and an owner-designated disposable domain already controlled for testing. Confirm it carries no customer traffic, mail, or other dependencies. A registration or purchase needs its own explicit authorization and spend limit; no real customer domain is an acceptable substitute.
2. **Allowed calls and limits:** list permitted reads and writes, exact domain and record names, run window, request limits, and spend ceiling. Begin with inventory and capability reads. Authorize only the specified DNS fixture changes; contacts, auto-renewal, auth codes, purchases, registry delegation, and DS/DNSKEY changes require separate explicit scope. An external DNS provider needs its own authorization. Keep custom nameservers/glue gated.
3. **Credential channel:** name an approved runtime secret store or equivalent secure channel for existing suitably scoped sandbox credentials. Do not put credentials, OTPs, passkeys, root registrar secrets, or connection URIs into chat, the repository, fixtures, screenshots, or logs. Credential/grant creation is a separate authorized action, not an implicit test prerequisite.
4. **Complete starting inventory:** capture the full provider-authorized zone, including CAA, unknown RR types, TTL, child NS, and relevant provider metadata and DNSSEC state. Store the snapshot securely and record its version/hash. Stop if fidelity cannot be established. Public DNS queries cannot establish a complete source inventory. Record source and destination authorization independently.
5. **Exact approved change:** create the immutable plan from that inventory and bind approval to tenant, domain, agent grant, state version, expiry, and exact changes. Recheck ownership, grant, and upstream state at execution. Apply once, retain the durable receipt, and read back. Report provider acceptance, authoritative visibility, and sampled propagation separately with timestamps/TTL; no global or immediate propagation claim and no claim of provider atomicity/CAS.
6. **Failure cases:** first use local fixtures for timeout, partial remove/add, malformed content, out-of-band edits, stale approval, revoked grants, and duplicate execution. Provider-side fault exercises require explicitly supported sandbox controls and additional scope. A timeout or partial result must enter reconciliation; never blindly repeat a write. Observing the old state alone does not prove a timed-out request cannot complete later. Require evidence of the provider's terminal outcome before recovery writes.
7. **DNSSEC and delegation:** mismatched parent DS and destination DNSKEY/signature evidence must fail closed; unknown state must remain blocked. This port offers nameserver proposals, not a validated migration executor. Enabling execution requires separate implementation/review and a supported transition tested against actual parent DS and destination DNSKEY/RRSIG, with complete authorized inventories, staged TTL waits, and source records preserved. Never remove DS merely to bypass a failed guard or trust `target_signed` as proof.
8. **Cleanup and evidence:** authorize exact cleanup changes only after the operation is terminal. Preserve resources and receipts when the outcome is unknown. Any restoration is a new reviewed write; it cannot undo lost mail or cached answers. Record candidate commit, permitted calls, redacted operation IDs, timestamps, state hashes, expected/actual results, and unresolved outcomes. Label simulations, historical recordings, and live sandbox observations separately.

Owner authentication also needs a bounded real-device acceptance check before rollout: passkey enrollment/sign-in, sensitive-action step-up, cancellation, repeated actions, recovery replay, and session revocation. Virtual-authenticator tests do not prove device UX. Do not enroll or alter a real owner's factors without authorization. Explain that passwordless passkeys replace a password; a claim of true two-factor authentication depends on the actual authentication factors and policy. Agents receive short-lived, revocable domain/operation grants through explicit incremental consent, never owner factors or registrar root credentials. Nameserver proposal consent does not grant execution.

## Separate queued Neon revocation gate

Review identified a pre-existing, non-DNS launch gate in `packages/api/src/recipes/routes.ts` and `packages/api/src/recipes/apply.ts`: enqueue-time scope checks do not revalidate the originating agent binding for a queued `postgres-neon` plan before provider effects. A plan queued before pause, revocation, expiry, or scope narrowing can still create a Neon project or obtain a database connection URI for planned Nest/Vercel targets using the owner's saved provider credential. Provider-connection authorization is distinct from the originating agent's still-current authority. This DNS port blocks agent DNS recipes and adds owner/hold checks; it does **not** close this separate binding gap.

Before enabling that agent workflow for public use, bind queued work to both applying and originating grant identities/version and recheck pause, revocation, family expiry, current domain access, and each target's `recipes.apply`/`secrets.write` scopes before dispatch and effects. Acceptance tests must enqueue and then pause, revoke, expire, or narrow the binding before the worker runs, with **zero provider-create, environment, or secret writes**. Already-dispatched effects need durable outcome handling; cancellation cannot promise to undo them. Keep this an explicit release blocker for the affected workflow until a separate reviewed fix or enforceable restriction is verified.
