# First live purchase blocked at "Save contact" — audit, 2026-10-08

Scope: the owner's first attempt to buy a name on mosshatch.com (Safari, 2026-10-08 05:24 PT, screenshot: the registrant contact form
answered "That did not work. Try again."), then the whole path from sign-in to the registrar, read live and in code. Method: the
production deployment and its logs (Vercel), the production database's operational rows (session timestamps, flags, alerts, migration
list, aggregate counts; no personal data), the deployed bundle, then the code on `main` (8b1f1b8) and local runs. Nothing was bought,
charged or registered; no production setting or row was changed.

## 1. What happened, from the evidence

| Time (UTC) | Evidence | Meaning |
|---|---|---|
| 12:07:32 | `sessions` row created (Safari), `last_seen_at` 12:07:33 | Sign-in from the open checkout sheet; the sheet then loaded the quote, documents and contact (the only requests that touch the session) |
| 12:07:33 → 12:22:33 | `idle_expires_at` 12:22:33 | The 15-minute idle rule (PLAN 4.3b, ST-52) ran out while the contact form was being filled: no request is sent while typing |
| ≈ 12:24 | screenshot, `POST /api/v1/contact` | The save was answered 401 `unauthorized`. The web app's `explain()` has no words for that code, so it showed the generic line |
| after | `contacts` 0 rows, `audit_log` has no `contact.saved`, `rate_counters` no `contact` bucket | No save ever reached the handler: the 401 came from the router before validation |

Two more things would have stopped the same save once signed in again:

- **The phone format.** The field asked for `+1.5555550100` (the EPP form, RFC 5733) and the server's schema accepted nothing else;
  the form was filled with `3107747497`. That answer (422 `invalid_contact`) at least had its own message, but the requirement itself
  was the defect: nobody types the EPP form, and the registrar adapter is the only thing that needs it.
- **No way back.** After a 401 the page still believed the person was signed in (the Account button, the registrant email line), the
  sheet stayed up, and pressing the button again gave the same line. Nothing refreshed the account or opened sign-in.

Not the cause, checked and ruled out: the deployed bundle (it is `main` 8b1f1b8 and carries the `invalid_contact` mapping); the CSRF
guard (sign-in and the invite flow pass it in the same browser); the live gate (the account has live access; the contact route is not
gated); the database (migrations through 1220 applied 04:29 UTC, `registrar_writes_paused` cleared by the owner 04:30, `orders_paused`
false, sell gate floor USD 5); the registrar project (answers `unauthorized` to an unsigned call, as it should); the Vercel function
(no `unhandled` line in seven days of runtime logs; the only logged lines are pg's `sslmode` deprecation warning on cold starts).

| ID | Finding | Sev | Fix | Proof |

## 2b. The second attempt (13:22 UTC): refused by the sell gate

With the fix above live, the contact saved (13:21:36) and **Buy domain & hatch** was pressed three times. Each `POST /api/v1/orders`
ran the quote, the availability check and the funding read against Openprovider (all answered 200), then the order transaction refused
with 503 `sell_gate` and rolled back: no order, no consent, no screening row. The arithmetic (`orders/create.ts`, `domains/gate.ts`):

| Available at Openprovider | Reserved | This order's wholesale (.com, member) | Left | Floor (`flags.sell_gate.min_funds_minor`) |
|---|---|---|---|---|
| USD 15.01 | 0 | USD 10.46 | USD 4.55 | USD 5.00 |

The sheet had said nothing beforehand (the quote's `sales_open` read only the pause flags), the refusal text landed below the sticky
button on a long sheet, and the hourly balance job reported the gate open (it compares free funds with the floor, not with the floor
plus a registration), so no alert was raised. Fixed in this change:

| ID | Fix | Proof |
|---|---|---|
| B1 | The quote answers the sell gate's own arithmetic before the click (`fundingOpenFor`: the hourly snapshot first, the registrar live only when the snapshot says no, so a top-up shows at once); `sales_open:false` with `sales_closed_reason:"funding"` disables Buy with the paused notice | `search.test.ts` AUD-P5/F3, `gate.test.ts` |
| B2 | The balance job raises `registrar_balance_underfunded` (warn, emailed to `MH_ALERT_EMAIL`, not a page: pausing writes would not help) when the gate is open but the cheapest registration would close it, and closes it after a top-up | `gate.test.ts`, `notifier.test.ts` |
| B3 | A refusal on the checkout sheet scrolls into view | code review |

**Owner action:** top up the Openprovider balance (USD 20 or more; GO-LIVE step 2), then press Buy again. Lowering the floor instead
(`update flags set value = '400' …`) would let this one order through with USD 0.55 to spare; topping up is the honest fix.

## 2c. The third attempt (13:53 UTC): the order was written, Stripe refused the Checkout Session

With the balance at USD 40.01 the sell gate passed: the order row, the consents, the screening row and the Stripe customer
(`cus_…`, the first live Stripe call) were all created at 13:53:43. Creating the Checkout Session was refused, the app answered 503
`payment_unavailable` ("Secure checkout couldn't open just now"), below the fold again, and recorded nothing about why. Reproducing
the exact request against the live account through the Stripe connector (a Session that names no order; none was created) gave the
reasons in order:

1. `custom_text cannot be used with Managed Payments, which is enabled by default on your account.` Stripe's merchant-of-record mode is on by
   default for the new account; Mosshatch is the merchant itself. Fixed in code: every Session sends `managed_payments[enabled]=false`
   (`stripe/params.ts`). Owner: also turn the account default off (Settings, Managed Payments).
2. `You must specify a tax code in all line items to calculate taxes. Alternatively you can set a default tax code on your tax settings.`
   The Products carry no tax code by design (C-44, the accountant's decision) and the live Tax settings have no preset. Owner: set the
   preset product tax code (Settings, Tax); `txcd_10000000`, General – Electronically Supplied Services, is the generic digital-goods
   code the catalog itself names; a line-item `tax_code` is not accepted by Checkout, so it must be the preset or the Products.

Also fixed: a refused Session is now logged (kind, status, code, parameter name) and raised as `stripe.checkout_refused`, an emailed
warning, so the next refusal is visible without a reproduction. Noted: the live account's statement descriptor prefix is `NICHOLAS`
(C-40 asks for `MOSSHATCH`), so a card statement would read `NICHOLAS* REGISTER`; Stripe may hold an individual account to the person's
name until the trade name exists (LAUNCH-CHECKLIST stage 5).

## 2d. The fourth attempt (15:53 UTC): paid, refused by Openprovider over unsigned terms, registered at 16:14 once they were signed

With the tax preset set (§2c) the Session opened, the card was authorized at 15:54:57 and the order reached `registering` at 15:55:03.
The registrar log shows Openprovider accept the customer record and refuse `CREATE_DOMAIN` with HTTP 500 and its code 309, which its
error-code list defines as the reseller account not having agreed to the current registration terms for the extension. The adapter
files every 5xx on a write as an unknown outcome (the right call for a gateway timeout, after which the create may have taken effect),
so the order moved to `outcome_unknown`; the reconcile polls at 15:58, 16:00 and 16:05 listed the account's domains and found nothing,
and left alone the order would have cancelled the hold on 2026-10-14 (`unknown_deadline`). The owner signed every contract under
Account, Contracts at about 16:05. The operator then resolved the first register operation as refused (code 309), returned the order to
`authorized` with an event recording why, and closed the stale alert; the next reconcile re-sent the create at 16:14:23 under a new
operation, Openprovider answered ACT at 16:14:36 (its order 30378066), the app read the domain back, captured USD 13.46 (no tax, a
California address) at 16:14:42, and untilwow.com hatched a Moss Hare.

Fixed in this change: the Openprovider adapter keeps a short list of provider codes that mean "refused before any effect", whatever
HTTP status carries them (309 is its first entry, on the evidence above; an unlisted code on a 5xx keeps the unknown-outcome path). Such
a refusal is `unavailable` and retryable, so the order machine parks the order in `registrar_unavailable`, emails `MH_ALERT_EMAIL` the
Contracts instruction once per order (`registrar_terms`, a warning, not a page: pausing registrar writes would not help), and retries
under the usual backoff until the terms are signed; the customer's sheet says the registrar is busy and the card only has a hold.
GO-LIVE §2 gains the contracts step it lacked, with the check that every extension on sale reads "Signed".
