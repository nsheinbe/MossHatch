# First live purchase blocked at "Save contact" — audit, 2026-10-08

Scope: the owner's first attempt to buy a name on mosshatch.com (Safari, 2026-10-08 05:24 PT, screenshot: the registrant contact form
answered "That did not work. Try again."), then the whole path from sign-in to the registrar, read live and in code. Method: the
production deployment and its logs (Vercel), the production database's operational rows (session timestamps, flags, alerts, migration
list, aggregate counts; no personal data), the deployed bundle, then the code on `main` (8b1f1b8) and local runs. Nothing was bought,
charged or registered; no production setting or row was changed.

## 1. What happened, from the evidence

| Time (UTC) | Evidence | Meaning |
|---|---|---|
| 12:07:32 | `sessions` row created (Safari), `last_seen_at` 12:07:33 | Sign-in from the open checkout sheet; the sheet then loaded the quote, documents and contact (the only requests that touch the session) |
| 12:07:33 → 12:22:33 | `idle_expires_at` 12:22:33 | The 15-minute idle rule (PLAN 4.3b, ST-52) ran out while the contact form was being filled: no request is sent while typing |
| ≈ 12:24 | screenshot, `POST /api/v1/contact` | The save was answered 401 `unauthorized`. The web app's `explain()` has no words for that code, so it showed the generic line |
| after | `contacts` 0 rows, `audit_log` has no `contact.saved`, `rate_counters` no `contact` bucket | No save ever reached the handler: the 401 came from the router before validation |

Two more things would have stopped the same save once signed in again:

- **The phone format.** The field asked for `+1.5555550100` (the EPP form, RFC 5733) and the server's schema accepted nothing else;
  the form was filled with `3107747497`. That answer (422 `invalid_contact`) at least had its own message, but the requirement itself
  was the defect: nobody types the EPP form, and the registrar adapter is the only thing that needs it.
- **No way back.** After a 401 the page still believed the person was signed in (the Account button, the registrant email line), the
  sheet stayed up, and pressing the button again gave the same line. Nothing refreshed the account or opened sign-in.

Not the cause, checked and ruled out: the deployed bundle (it is `main` 8b1f1b8 and carries the `invalid_contact` mapping); the CSRF
guard (sign-in and the invite flow pass it in the same browser); the live gate (the account has live access; the contact route is not
gated); the database (migrations through 1220 applied 04:29 UTC, `registrar_writes_paused` cleared by the owner 04:30, `orders_paused`
false, sell gate floor USD 5); the registrar project (answers `unauthorized` to an unsigned call, as it should); the Vercel function
(no `unhandled` line in seven days of runtime logs; the only logged lines are pg's `sslmode` deprecation warning on cold starts).

## 2. Fixed in this change

| ID | Finding | Sev | Fix | Proof |
|---|---|---|---|---|
| A1 | The session idles out under a person who is typing (no request is made while filling a form), and the save then fails | S2 | `lib/session.ts` `useSessionKeepalive`: real input (a key, a pointer, a field) asks `GET /api/v1/session` at most every 5 minutes, which renews the idle clock. Nothing is sent while the tab is left alone, so ST-52 still ends an abandoned session | code review; the server already touches the session on that request (`http/session.ts` `resolveSession`) |
| A2 | A 401 on a signed-in page shows "That did not work. Try again." and leaves the page believing the person is signed in | S2 | `sessionEnded()`: on a 401 the page asks the server who it is; when nobody, the account is cleared, sign-in opens with a one-line reason (store `accountNotice`), and the checkout sheet with the chosen name is still there after sign-in. Used by the contact form, the Pay button and the domain contact change; `explain()` also has words for `unauthorized`, `csrf` and `internal` as the fallback | `explain` cases; e2e account journey unchanged |
| A3 | The contact form demands the EPP phone form `+1.5555550100`; the server refuses anything else | S2 | `packages/core/phone.ts` `normalizePhone`: a number typed any usual way (`(310) 774-7497`, `020 7946 0958` with GB, `+44 (0)20 …`, `0049 …`, `011 44 …`, with an extension) becomes `+CC.number`; one shared server schema (`orders/registrant.ts` `RegistrantBody`) for checkout, transfer-in and the domain contact change; the two forms read it on the page first and say what works | `phone.test.ts` (6 cases, 40 numbers), `account.test.ts` (stored EPP form for four spellings, two refusals), e2e account journey with `(555) 555-0100` |
| A4 | What was typed is lost when sign-in interrupts the save (the sheet re-keys on the account) | S3 | The contact form keeps the draft in memory for the same address until it is saved; never in storage | code review |
